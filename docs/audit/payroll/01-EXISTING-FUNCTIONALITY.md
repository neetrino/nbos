# Payroll audit — existing functionality

**Audit date:** 2026-09-26. **Method:** read-only source, schema, canon and test inspection, plus 45 isolated tests (see [05](05-PAYROLL-TEST-REPORT.md)). **Meaning of “implemented”:** a code path exists; it does not assert that the path works with current production data. Paths and line numbers below refer to the repository at audit time.

## What the product does today

NBOS represents an employee's monthly pay as a fixed amount plus bonuses. A compensation profile is a version of the employee's fixed amount and linked policy choices. Finance creates one payroll run per month; it contains one salary line per included employee. An approved run creates expense cards, and payments recorded against those expenses update paid and remaining amounts. The employee Wallet shows a read-only projection of salary and bonuses. The product canon defines this model in `docs/NBOS/03-Business-Logic/03-Bonus-Payroll-Logic.md:5-19` and `docs/NBOS/02-Modules/04-Finance/05-Bonus-and-Payroll.md:576-629`.

## Data model and boundaries

The durable chain is `Employee` → `CompensationProfile` → `PayrollRun`/`SalaryLine` → `Expense`/`ExpensePayment`. Bonus work uses `BonusEntry` → `BonusRelease` → `SalaryLine`; a `ProductBonusPool` is a derived order-level summary. `PayrollRun.payrollMonth` is unique; `SalaryLine` is unique per run and employee; `PayrollBonusAllocationDraft` is unique per run, employee and order. `BonusEntry` also has database partial unique indexes for sales accruals (schema comment at `packages/database/prisma/schema/finance.prisma:586-588`). Schema evidence: `packages/database/prisma/schema/finance.prisma:530-805`.

Employees can belong to multiple departments (`packages/database/prisma/schema/rbac.prisma:50-62`), and Salary Board exposes those memberships for filtering (`apps/api/src/modules/payroll-runs/payroll-salary-board.ts:53-62,152-163`). Payroll still creates a single employee line per month. No department split or cross-project salary allocation was established by this audit. A delivery participant can receive bonus entries from multiple orders/projects because each entry names an employee, order and project (`packages/database/prisma/schema/finance.prisma:530-536`).

## What “implemented” does not establish

The tests run here use mocked Prisma data. No live database, deployed API, production configuration, job queue or browser was exercised. Therefore actual employee records, current policy values, schema migration state, payout accuracy and user-visible behavior remain **implemented but not verified in a live environment**. The more specific gaps and defects are in [03](03-REQUIREMENTS-GAP-ANALYSIS.md) and [04](04-FUNCTIONAL-DEFECTS.md).
