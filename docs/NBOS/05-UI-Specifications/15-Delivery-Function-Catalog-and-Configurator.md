# Каталог функций, Конфигуратор продукта и Wallet — UI v2

**2026-09-18 · целевая спецификация, не отчёт о готовом UI.**

Поведение: [бизнес-канон](../03-Business-Logic/11-Delivery-Compensation-Configurator.md). Технический контракт и фазы: [пакет реализации](../../implementation/delivery-compensation/README.md).

| Место                                           | Назначение                                                                                                      | Видимые деньги                                          |
| ----------------------------------------------- | --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------- |

| `/my-company/delivery-norms` — Core & Function  | Три таба: Core, Functions, Role rates. Старый `/my-company/function-catalog` редиректит на `?section=functions` | Units, цена и ставки — только Owner/CEO                 |

Не создавать новый верхнеуровневый модуль Sidebar. В шапке My Company один пункт **Core & Function** рядом с Roles & Seats. Право на каталог не требует доступа ко всем HR/Compensation данным: без RULES VIEW видны только Functions и таб «Основное».

## 2. Каталог функций

Desktop: заголовок «Каталог функций», поиск, категории, фильтр доступности; сетка компактных карточек с иконкой, названием и коротким описанием. Mobile: одна/две колонки без горизонтального скролла. Это визуальный каталог крупных возможностей, не плоский checkbox checklist задач.

Карточка: иконка, название, категория, краткое назначение. Для Owner/editor дополнительно draft/active/archived и «норматив не настроен»; команда по умолчанию видит опубликованную библиотеку. Числовые units, цены, зарплаты, employee rates в общей сетке отсутствуют.

Действия:

- чтение: открыть sheet;
- content editor: создать черновик инструкции/редактировать контент в своих правах;
- Owner/CEO: настроить расчёт, опубликовать/архивировать;
- архив скрывает выбор для новых продуктов, но существующие привязки остаются читаемыми.

Owner может seed-ить/создать функцию без units. Не показывать её как бесплатную. При публикации для расчёта требуется complete role vector: для каждой роли **Нужен**, **Если есть** или **Нет**. Пустое число у первых двух блокирует публикацию; явный 0 у **Нужен** оставляет слот.

## 3. Sheet функции — одна карточка, разные DTO

Раздел «Инструкция»:

1. Название, назначение, что входит/не входит.
2. Критерии готовности.
3. Пошаговое выполнение, нюансы, типовые ошибки.
4. Ссылки, изображения, файлы, примеры.
5. Версия инструкции, автор и дата обновления.

Rich text использовать из существующего редактора; безопасный renderer, санитизация ссылок/HTML. Изображения/файлы — через существующий FileAsset/Drive upload и ACL. Не делать произвольную загрузку по URL сервером и отдельный публичный bucket. Отсутствующий доступ к файлу показывает безопасное сообщение, не подписанный download URL.

Раздел «Расчёт» существует только для Owner/CEO и загружается отдельным разрешённым запросом:

- units по шести ролям;
- «Входит в базу для…» — выбор ядра по виду продукта;
- действующая версия, дата действия, история;
- создание новой финансовой версии, preview влияния только на новые расчёты;
- ссылки на централизованные тарифы ролей (не копировать разные тарифы в каждую функцию).

Не передавать скрытый financial JSON всем пользователям и не полагаться на CSS. Для Finance без права финансовых нормативов этот раздел также отсутствует. Инструкцию можно редактировать независимо от финансовой версии; её сохранение не вызывает пересчёт бонусов.

В контексте продукта sheet дополнительно показывает локальную заметку и параметры конкретной реализации. Они не записываются в общую инструкцию каталога. Инструкции могут обновляться; перед показом новой версии обозначить дату и дать историю. Изменение инструкции не означает согласованное изменение scope уже работающего проекта.

## 4. Units, профили и тарифы

Страница Core & Function, не вкладки Compensation. Ставки ролей остаются на странице; цена продажи живёт в sheet карточки.

- **Core**: сетка видов как invoice-карточки (до трёх колонок): статус, крупный Sales, units, «в базе». Клик открывает sheet ядра: Состав · Units · В базе · Sales · Комплекты. Units — число слева и отдельная заполненная кнопка вида слота справа. В базе — поиск и выбранные функции отдельными карточками. Состав приходит вместе с профилем (label/note), без второго ожидания. Сохранение пишет черновик. Одна кнопка **Publish** в правом верхнем углу шапки выпускает все сохранённые черновики этого ядра (профиль + цена). Комплекты привязаны к виду, не к отдельному экрану.
- **Functions**: invoice-карточки в том же языке, что Core (Sales + units справа). Список — только поля карточки. Первая страница — видимая порция; следующие страницы — по скроллу или при выборе категории / поиске, без немедленной догрузки всего каталога. Полный текст инструкции — в `GET /:id` при открытии sheet. Sheet функции: Основное · Units · Sales. Publish в шапке выпускает черновик units и цены. Если есть градация, селектор объёма стоит в Units и в Sales; цель цены тогда `TIER`.
- **Role rates**: шесть строк на странице. Редактировать раскрывает «было / стало»; сохранить пишет черновик, опубликовать — отдельная кнопка.
- Зачисление V2 — компактный переключатель над табами, не карточка и не sheet.

Публикация показывает: какие новые расчёты используют версию, что существующие планы не меняются. Ошибка неполной настройки привязана к конкретной роли/полю. Числа из fixtures не должны выглядеть production-default.

## 5. Конфигуратор конкретного продукта

Общий компонент в Product page и Delivery sheet. Вкладка «Функции» заменяет legacy Bonus-вкладку; другие существующие рабочие tabs остаются. Не копировать весь старый макет Delivery ради нового таба.

Верхний блок: тип продукта/category (существующие значения). Основы реализации, трёх режимов дизайна и AI-reviewer на экране нет. Размера расчёта нет. Под ядром и под каждой дополнительной функцией — ползунок объёма ×0.0…×2.0 (шаг 0.1, подпись ×коэффициент, «Стандарт» на ×1.0). Уход со стандарта открывает причину; без сохранённой причины значение не пишется. В шапке дополнительных функций тот же ползунок пишет один коэффициент на все добавленные строки. Расчётная цена в конструкторе сделки масштабируется тем же числом. На доработке ползунка ядра нет. Карточка доски показывает, что стандарт изменён, если ядро или добавленная функция не ×1.0.

**Конструктор на сделке (до появления Product).** На product-like сделке продавец собирает состав: каталог функций + клик по комплекту (replace набора) + ручная правка. Видна цена продажи (ядро + extra). Units итогом — только Owner/CEO. Цитата не перезаписывает сумму сделки. После Won extra-функции черновика копируются в конфигурацию продукта; included-in-base берётся с профиля, не из комплекта. Публичная витрина — этап 3, тем же каталогом, без units.

Ниже — активные функции в виде карточек:

- иконка и название;
- «Включено в базу» либо «Дополнительная функция»;
- при необходимости состояние работы «не начато / в работе / принято»;
- действие открыть инструкцию;
- локальное описание; никаких units, стоимости, зарплаты или денежных diff.

Кнопка «+ Добавить» у actor с CONFIGURE permission открывает общий каталог, уже выбранные функции не предлагаются повторно. Включённые в базу показаны активными сразу и не дают доплаты. Поиск/категории сохраняются при возврате из инструкции. Создание новой платной функции из picker доступно только имеющему право на финансовый каталог; PM не получает навязанную форму запроса units у CEO.

Starting: draft Save/Cancel, явное «Конфигурация проверена» с автором/временем; любое изменение scope/команды снимает подтверждение. Ошибка отсутствующего норматива не раскрывает числа, Owner получает ссылку в настройки.

После Development: Save показывает рабочий diff («добавлена интеграция X», «изменён исполнитель») и reason; финансовые результаты появляются только в кошельках/Finance. Не обращаться к закрытому financial preview для показа обычному PM. Политика изменилась между загрузкой и сохранением — `409`, обновить preview, не сохранить молча.

On Hold: допустимые изменения сохраняются с обычным audit, автопереход в Active не происходит. Done/Cancelled: read-only. Legacy product: banner «Новая модель не включена», без требований задним числом; adoption — Owner-only отдельное действие.

## 6. Переход в Development

Использовать существующие stage actions и механизм отображения blockers. Новые blockers ведут в поля конфигуратора или команды; обычному пользователю возвращать только причины «норматив не настроен», «назначьте исполнителя роли», «подтвердите конфигурацию».

Кнопка перехода не создаёт клиентский бонус отдельным последующим запросом. Сервер подтверждает одновременно lifecycle и план. При успехе: обычный toast о стадии, конфигурация read-only по старым финансовым версиям с доступными scope changes. Кошельки инвалидируются/уведомляются после commit. Денежный toast в Delivery запрещён.

## 7. Окно замены участника

Открывается при изменении слота после появления плана в любом UI: Delivery, Product, Extension. Закрытие без Save возвращает старого исполнителя; нельзя сначала сохранить команду, а потом необязательно открыть распределение.

Поля:

- роль, прежний и новый участник;
- базовая часть: два ПУСТЫХ поля долей;
- дополнительные оплачиваемые функции этой роли: строки с ПУСТЫМИ долями;
- reason, безопасная информация о наличии финансового ограничения;
- Save/Cancel.

Не ставить default, не заполнять проценты из стадии/числа закрытых задач. Даже 0/100 пользователь вводит сам. При повторной замене UI явно пишет «распределяется доля сотрудника X» и сохраняет доли остальных. Нулевые компоненты без денежного обязательства можно обозначить «распределение не требуется» без суммы; не вынуждать распределять отсутствующий бонус.

Обычный PM видит проценты участия, но не units и суммы. Owner/Finance при необходимости открывает финансовые ограничения в своём отдельном рабочем пространстве. Ошибка переноса зарезервированного/выплаченного не раскрывает PM размер чужой выплаты.

## 8. Wallet

Расширить существующие bonus rows и product breakdown, не создавать ещё один кошелёк. Начиная с первого Development сотрудник видит личный план по продукту/Extension. До этого черновой расчёт Owner не отображается как обещанный доход.

Деталь: продукт, роль/работа, плановый бонус, статус, текущий доступный release, payroll/paid facts, изменения «добавлена функция», «перераспределение работ». Все суммы scoped к текущему сотруднику; публичного delivery pool total нет. Units, tariffs, чужие получатели/суммы и полный calculationSnapshot не возвращаются.

Плановая сумма ≠ «доступно снять». Существующие стадии бонуса и фактические частичные платежи сохраняются. Для одного человека в нескольких ролях UI может суммировать в карточке продукта, но раскрывает собственные отдельные роли, без удвоения.

## 9. Общие состояния и UX-гейты

- Loading skeleton; empty catalogue объясняет отсутствие опубликованных функций; ошибка загрузки с retry без потери draft.
- Dirty draft: Save/Cancel и предупреждение при закрытии; при nested sheet сохраняются выбор и scroll.
- Double click/save: одна операция; concurrent update `409` с перезагрузкой и видимым diff.
- Forbidden/not found не раскрывают чужие данные; прямой URL проверяется сервером.
- Полная клавиатурная навигация, подписи icon-buttons, focus-return к вызывающей карточке, доступный dialog на mobile.
- Использовать существующие shared Sheet/Dialog, feature cards, typography/theme; никаких новых UI libraries.
- EN/RU/HY ключи согласно действующей i18n политике; не хардкодить русские сообщения в API или JSX.
- Архивный каталог и отсутствующие вложения не разрушают исторические проекты.
- История Product показывает рабочие изменения без financial payload. Закрытый audit доступен только соответствующей роли.

## 10. Проверка экранов

1. Owner публикует функцию/профиль/тарифы; PM читает ту же инструкцию без раздела расчёта и без финансовых данных в Network response.
2. PM создаёт scope в Product; тот же выбор виден в Delivery и после reload.
3. Starting → Development: суммы возникают в Wallet, но отсутствуют в Delivery DOM, JSON, notifications и общедоступной истории.
4. Добавление included-функции не увеличивает бонус; extra-функция увеличивает только затронутые роли.
5. Замена участника из обоих entry points требует пустые поля заполнить вручную.
6. Все сценарии выполняются с desktop и mobile шириной; screen-reader labels и focus не теряются.

Это обязательный финальный UI, не набор placeholder tabs. При отсутствии браузерной проверки фиксировать ограничение, а не помечать visual QA выполненной.
