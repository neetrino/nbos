# Определение ролей

> NBOS Platform — ролевая модель компании Neetrino

## Обзор

В NBOS каждый сотрудник имеет одну или несколько ролей, определяющих его зону ответственности и уровень доступа к модулям платформы. Роли спроектированы по принципу **минимально необходимого доступа**: каждый видит только то, что нужно для выполнения его работы.

**Дополнение 2026-09-18/19:** для продуктов [Delivery Compensation v2](../03-Business-Logic/11-Delivery-Compensation-Configurator.md) delivery-бонус роли считается units × тариф роли. Split 70/30 ниже — только legacy. Сотрудник видит свои деньги в Wallet, не units и не чужие суммы на Delivery.

## 1. CEO (Генеральный директор)

**Назначение:** Операционное управление компанией. Самая сильная **роль** (RBAC), не security root платформы.

| Параметр                 | Описание                                                                                                                                                                            |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Ключевые обязанности** | Определение стратегии, утверждение крупных сделок, разрешение спорных ситуаций, управление партнёрской сетью, контроль P&L                                                          |
| **KPI**                  | Общая выручка, чистая прибыль, количество активных проектов, retention клиентов, рост команды                                                                                       |
| **Видит**                | Все операционные модули, все проекты, Drive, CRM, финансы, payroll. Vault: Team/Company `NORMAL` и все project `NORMAL` без membership. `RESTRICTED`/`SECRET` только с явным grant. |
| **Не видит**             | Чужие Personal credentials; `OWNER_ONLY`; полный vault export; Platform Owner identity                                                                                              |

**Особенности:**

- Не является Platform Owner. Security root — `isPlatformOwner` (см. `16-Settings-Admin/03-Platform-Owner-Security-Architecture.md`).
- Не может назначить Founder или второго CEO; не может деактивировать Founder.
- Emergency vault: только запрос, approve делает Founder.

## 1b. Platform Owner / Founder

**Назначение:** Защищённая identity владельца платформы (не RBAC-роль). В production якорь `NBOS_FOUNDER_EMPLOYEE_ID`.

| Параметр      | Описание                                                                          |
| ------------- | --------------------------------------------------------------------------------- |
| **Видит**     | Все корпоративные credentials, включая `OWNER_ONLY`                               |
| **Sovereign** | Full vault export, ownership transfer, emergency approve, CREDENTIALS scope `ALL` |

Legacy role slug `owner` может остаться у Founder для совместимости (`assignable=false`), но проверки security root используют только `isPlatformOwner`.

## 2. Seller (Продавец / Менеджер по продажам)

**Назначение:** Ведение клиента от первого контакта до подписания договора и получения первой оплаты.

| Параметр                 | Описание                                                                                                                                      |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------- |
| **Ключевые обязанности** | Обработка лидов, ведение сделок по pipeline, подготовка коммерческих предложений, создание Invoice на предоплату, оформление Extension-сделок |
| **KPI**                  | Количество закрытых сделок, конверсия Lead→Deal→Won, средний чек, срок закрытия сделки, объём продаж за период                                |
| **Видит**                | CRM (лиды, сделки), Заказы (суммы invoice и факт оплаты), Контакты, Компании, Календарь (свои встречи), Мессенджер (клиентские каналы)        |
| **Не видит**             | Расходы компании, зарплаты, бонусы других, пароли/credentials, Scrum-доску и задачи разработки, внутренние проектные чаты                     |

**Бонусная система:**

- Sales bonus считается по независимым ставкам Seller / Assistant из Bonus Policy, выбранным по `From` сделки и типу оплаты
- Бонус запускается после первого квалифицирующего платежа по Deal / Order и не зависит от product delivery pool

## 2b. Ассистент на сделке — уровень участия, не роль

**Назначение:** Помощь основному продавцу на конкретной сделке.

Ассистент — это **не Permission Role**. Когда сделку ведут два человека, оба они Seller (или один из них Head of Sales), а различает их роль **в этой сделке**: `Deal.sellerId` — основной, `Deal.sellerAssistantId` — помощник. На другой сделке те же двое могут поменяться местами.

| Параметр             | Описание                                                                   |
| -------------------- | -------------------------------------------------------------------------- |
| **Где живёт**        | `Deal.sellerAssistantId`, не роль и не seat                                |
| **Какая роль нужна** | `seller` (или `head-sales`) — отдельного slug у ассистента нет             |
| **Что даёт участие** | Доступ к сделке, её звонкам, click-to-call, чату и клиенту наравне с owner |
| **Бонус**            | Отдельная строка начисления по ставке Assistant из Bonus Policy            |

Почему не роль: права ассистента ничем не отличаются от прав Seller, поэтому отдельный slug не давал бы ничего, зато делал бы «повышение до ассистента» постоянным свойством человека вместо факта об одной сделке. Вся видимость (`deal-list-responsibility.where.ts`, доступ к записям звонков, participants в мессенджере, граф команды) и всё начисление бонусов читают `sellerAssistantId`.

> **Историческая справка:** до 2026-09 канон описывал `seller-assistant` / `role-seller-assistant` как Permission Role. Роль никогда не создавалась ни одной миграцией и не давала ничего сверх `seller`; ссылки на неё удалены из кода.

## 3. PM (Project Manager / Проект-менеджер)

**Назначение:** Управление доставкой проекта — от получения заказа до сдачи клиенту и перехода на Maintenance.

| Параметр                 | Описание                                                                                                                                                                                                         |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Ключевые обязанности** | Приёмка проекта от Seller (Handoff), планирование спринтов, управление задачами, контроль дедлайнов, коммуникация с клиентом, контроль чек-листов качества, тriage обращений поддержки                           |
| **KPI**                  | Количество проектов в срок, среднее отклонение от дедлайна, количество багов после сдачи, удовлетворённость клиента, загрузка команды                                                                            |
| **Видит**                | Projects Hub (все данные проекта), задачи, Scrum/Kanban, пароли проекта (назначенные команде), Drive проекта, проектные чаты, Support Tickets, календарь, финансовую сводку проекта (суммы заказа, статус оплат) |
| **Не видит**             | Финансы уровня компании (P&L, расходы, зарплаты других), секретные пароли компании, CRM-сделки (кроме привязанных к его проектам)                                                                                |

**Бонусная система:**

- Процент по Product / Extension зависит от Product/Extension bonus policy: category/type, complexity, role и configured rate
- Выпускается через Product Bonus Pool после сдачи Product / Extension и по доступному funding

**Временная функция:** Пока нет отдельного специалиста поддержки, PM выполняет triage Support Tickets.

## 4. Developer Backend (Разработчик Backend)

**Назначение:** Основной ответственный за разработку продукта в Delivery — backend и общая техническая доставка.

| Параметр                 | Описание                                                                                                                                                                   |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Slug / id**            | `developer` / `role-developer` (display name: **Developer Backend**)                                                                                                       |
| **Ключевые обязанности** | Выполнение задач из Scrum-доски, написание кода, code review, тестирование, деплой, заполнение технических данных (env, credentials); **основной accountable** по продукту |
| **KPI**                  | Количество закрытых задач, story points за спринт, количество багов в production, соблюдение оценок по времени                                                             |
| **Видит**                | Назначенные задачи, Scrum/Kanban-доску проекта, пароли проекта (назначенные ему), Drive проекта, проектные чаты, свою доску бонусов                                        |
| **Не видит**             | Финансовые данные (суммы сделок, оплаты, расходы, зарплаты), CRM (лиды, сделки), заказы, пароли других проектов, секретные пароли                                          |

**Назначение на Product:** поле `developerId` / seat `DEVELOPER` — **primary**, accountable.

**Бонусная система:**

- **Новая модель:** units Backend × тариф Backend; 70/30 не применяется. Деньги — в Wallet.
- **Legacy:** доля **delivery developer pool** (PM/Designer вне этого пула): **70%** Backend, если Frontend — **другой** сотрудник; если Frontend не назначен или совпадает с Backend — **100%** Backend. Frontend без Backend запрещён.
- Выпуск выплаты — через существующий Product Bonus Pool / funding (Classic и Subscription). Плановый бонус v2 появляется при первом Development, не как немедленная выплата.

## 5. Developer Frontend (Разработчик Frontend)

**Назначение:** Помощь в delivery по frontend в рамках продукта; не primary accountable.

| Параметр                 | Описание                                                                                                               |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------- |
| **Slug / id**            | `developer-frontend` / `role-developer-frontend` (display name: **Developer Frontend**)                                |
| **Ключевые обязанности** | Frontend-задачи из Scrum-доски, UI-реализация, участие в code review и тестировании под руководством Developer Backend |
| **KPI**                  | Количество закрытых задач, соблюдение оценок, качество UI-сдачи                                                        |
| **Видит**                | **Та же матрица доступа**, что у Developer Backend (см. Access Matrix)                                                 |
| **Не видит**             | Финансовые данные, CRM, заказы, пароли вне назначенных проектов, секретные пароли                                      |

**Назначение на Product:** поле `frontendDeveloperId` / seat `DEVELOPER_FRONTEND` — **не primary**, assisting.

**Бонусная система:**

- **Новая модель:** собственные units Frontend × тариф Frontend; отдельная роль, не 30% от пула Backend.
- **Legacy:** доля **delivery developer pool**: **30%** Frontend только если это **другой** сотрудник; если Frontend не назначен или совпадает с Backend — отдельная строка Frontend не создаётся, Backend получает **100%** developer pool. Frontend без Backend запрещён.

**Отличие от Junior Developer:** полный доступ Developer (Scrum-доска, проектный контекст), а не только явно назначенные задачи.

## 6. Junior Developer (Младший разработчик)

**Назначение:** Выполнение назначенных задач под контролем старшего разработчика или PM.

| Параметр                 | Описание                                                                                                              |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------- |
| **Ключевые обязанности** | Выполнение конкретных назначенных задач, работа по инструкциям и чек-листам                                           |
| **KPI**                  | Количество закрытых задач, качество выполнения, скорость обучения                                                     |
| **Видит**                | Только назначенные ему задачи, только явно предоставленные пароли, ограниченный Drive проекта                         |
| **Не видит**             | Полную Scrum-доску (только свои задачи), финансы, CRM, заказы, пароли проекта (кроме явно выданных), секретные пароли |

**Отличие от Developer Backend / Frontend:** Минимальный доступ — видит только то, что ему явно назначили. Не видит общую картину проекта. Отдельная роль; **не** объединяется с Developer Frontend.

## 10. Finance Director (Финансовый директор)

**Назначение:** Полный контроль финансовой стороны бизнеса — от выставления счетов до P&L.

| Параметр                 | Описание                                                                                                                                                                                                                   |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Ключевые обязанности** | Управление счетами (Invoice), контроль оплат, ведение расходов (плановых и внеплановых), подписочная сетка, начисление бонусов и зарплат, автоматизация финансовых процессов, работа с госсервисами для выставления счетов |
| **KPI**                  | Процент вовремя оплаченных счетов, просроченная дебиторская задолженность, точность финансового плана, время закрытия месяца                                                                                               |
| **Видит**                | Заказы, Invoices, Payments, Subscriptions Grid, Expenses, Salary Board, Bonus Ledger, P&L, финансовые дашборды, контакты и компании (для выставления счетов)                                                               |
| **Не видит**             | Scrum/Kanban-доски, задачи разработки, пароли/credentials, технические детали проектов                                                                                                                                     |

**Ежедневный процесс:**

1. Проверка банковского счёта → отметка оплаченных Invoice
2. Запуск автоматизации → отправка напоминаний неоплатившим клиентам
3. Контроль просроченных платежей → эскалация

## 15. HR Manager (Менеджер по персоналу)

**Назначение:** Найм, адаптация, офбординг, обучение и корпоративная культура.

| Параметр                 | Описание                                                                    |
| ------------------------ | --------------------------------------------------------------------------- |
| **Slug / id**            | `hr-manager` / `role-hr-manager`                                            |
| **Ключевые обязанности** | Рекрутинг, онбординг, офбординг, программы обучения, политики и документы   |
| **KPI**                  | Time-to-hire, retention, training completion                                |
| **Видит**                | Сотрудников и оргструктуру с правом изменения, документы, задачи онбординга |
| **Не видит**             | Зарплаты, бонусы, любые финансовые модули, CRM, проекты                     |

Payroll принадлежит Finance, поэтому у HR закрыты `FINANCE_SALARY` и `FINANCE_BONUSES`. Сотрудников не удаляют, а проводят через офбординг, поэтому `COMPANY` даёт VIEW / EDIT / ADD, но не DELETE.

Реактивация уволенного сотрудника разрешена держателям роли `hr-manager` — в том числе когда роль дополнительная, а не основная. Раньше проверка смотрела на департамент со слагом `hr`; после переименования отдела она перестала совпадать и право молча схлопнулось до CEO и Platform Owner. Слаг роли стабилен, потому что роль системная и в Settings заблокирована на переименование.

| **Slug / id**            | `operations-manager` / `role-operations-manager`                            |
| **Ключевые обязанности** | Ведение SOP и чеклистов, координация внутренних процессов, офис             |
| **KPI**                  | SOP coverage %, tool uptime, process efficiency                             |
| **Видит**                | Чеклисты и SOP полностью, оргструктуру с правом изменения, Drive, документы |
| **Не видит**             | Settings платформы, CRM, инвойсы и платежи, зарплаты и бонусы               |

`SETTINGS` остаётся закрытым: администрирование платформы — не операционная функция, а зона CEO / Platform Owner.

## 17. Accountant (Бухгалтер)

**Назначение:** Исполнение финансовых операций: счета, платежи, налоги, отчётность.

| Параметр                 | Описание                                                                     |
| ------------------------ | ---------------------------------------------------------------------------- |
| **Slug / id**            | `accountant` / `role-accountant`                                             |
| **Ключевые обязанности** | Выставление и проведение счетов, платежи, расходы, отчётность в гос. системе |
| **KPI**                  | Overdue invoices, срок закрытия периода, корректность отчётности             |
| **Видит**                | Инвойсы, платежи и расходы полностью; зарплаты и бонусы только на чтение     |
| **Не видит**             | Оргструктуру на изменение, audit logs, CRM, проекты                          |

Отличие от Finance Director: бухгалтер исполняет, но не решает. Бюджетирование, P&L, изменение оргструктуры и audit logs остаются у Finance Director.
