# Локализация интерфейса NBOS

Дата решения: 2026-09-12. Статус: архитектура утверждена; первый EN/RU срез реализован в рабочем дереве. HY выключен. Production rollout не входит в этот срез.

Этот документ является решением об архитектуре локализации и заменяет прежнее ограничение TECH_CARD «English only / i18n не требуется (v1)». Он не меняет бизнес-значения сущностей, права, финансовые расчёты и правила времени.

## Область первого релиза

EN/RU: общая навигация desktop/mobile, меню аккаунта и выбора темы/языка, главный Dashboard (Control Center), персонализация, виджеты, заметки, ссылки, каталог приветствий, состояния и четыре сценария создания из Dashboard: Task, Meeting, Lead, Expense. Переводятся используемые ими общие поля, селекторы, валидация, подтверждения и сообщения результата.

Страницы My Account и My Wallet за пределами их пунктов меню, полные страницы остальных модулей, глобальный поиск и центр уведомлений, auth-страницы, письма, PDF/экспорты и внешние сообщения — последующие этапы. Общие кнопки открытия этих поверхностей переводятся сейчас. Дополнительные вложенные сценарии создания сущностей внутри relation picker не расширяют релиз рекурсивно: их реестр и границы фиксируются при инвентаризации. Нельзя объявлять всю платформу русифицированной по готовности этого релиза.

HY предусмотрен архитектурой, но не доступен в переключателе до готовности пилота и согласования терминов. RTL не входит в текущий объём.

## Решение: библиотека и каталоги

Использовать next-intl с Next.js App Router без языковых префиксов URL. Сохранить маршруты, ссылки, auth proxy и PWA. Совместимую версию выбрать и зафиксировать при реализации; не обновлять остальной стек ради i18n.

Предполагаемая структура реализации:

- `apps/web/src/i18n/`: конфигурация запроса, серверная загрузка, выбор словарей и форматирование.
- `apps/web/src/messages/en/` и `ru/`: common, navigation, account, dashboard и каталоги затронутых форм.
- `packages/shared`: только реально разделяемые коды локалей и контракты, без зависимости NestJS от next-intl и React.

Исходный каталог EN; стабильные семантические ключи, например `dashboard.actions.newTask`. Не использовать английскую фразу как идентификатор. Общие действия переиспользуются; одинаковое слово с разным бизнес-смыслом может иметь разные ключи. Перевод выбирается при рендере, а не один раз при импорте модуля. Реестры хранят ключи, не захваченные переведённые строки.

Использовать ICU для интерполяции и множественного числа. Не склеивать предложения. Проверять совпадение ключей, параметров и корректность ICU. Для готового участка пропуск RU — ошибка проверки. В production при неожиданном пропуске показывать английский текст с теми же параметрами, а не технический ключ. Fallback реализовать и проверить явно: одного подключения библиотеки недостаточно. Отсутствие строки в EN также считается дефектом.

Загружать только необходимые каталоги; не передавать будущие словари всей платформы каждому клиентскому экрану. Пользовательские данные не включать в статические каталоги.

## Персональная настройка и загрузка

Источник истины — новое поле `Employee.interfaceLocale`, строка с default `en`; поддерживаемые значения контролируются общим allowlist. Сейчас writable/enabled: `en`, `ru`; `hy` зарезервирован для будущего релиза, но пока отклоняется при сохранении. Строка позволяет добавлять языки без изменения PostgreSQL enum. Не помещать глобальную настройку языка в DashboardPreference и не связывать её с клиентским reminderLanguage или Product.languages.

Целевой контракт: `GET /api/v1/me/preferences` → `{ interfaceLocale }`; `PATCH /api/v1/me/preferences` принимает `{ interfaceLocale }` и возвращает сохранённое значение. Это новая узкая поверхность, а не изменение контрактов бизнес-модулей. Использовать текущую аутентификацию, BFF и DTO-паттерны; OpenAPI и frontend-типы обновить вместе. Пользователь определяется сервером, employeeId от клиента не принимается. Неверная локаль → 400 без записи. Настройку может менять любой аутентифицированный сотрудник для себя независимо от доступа к Dashboard или HR.

Для аутентифицированного запроса сохранённое значение пользователя имеет приоритет над cookie. Запрос предпочтений выполняется через существующий безопасный серверный API/auth-путь без нового механизма refresh и без помещения изменяемой настройки исключительно в JWT. Сервер и первый клиентский рендер получают одну локаль, словари и `html lang`.

Cookie — вспомогательная настройка браузера, не источник прав или идентичности. До входа использовать валидную cookie, иначе EN; автоматический выбор по браузеру в первом релизе не нужен. Для вошедшего пользователя при недоступной БД/API использовать EN, не записывать этот fallback в БД и не применять потенциально чужую cookie. При выходе очищать пользовательский кеш предпочтений и cookie; следующий вход читает профиль нового пользователя. Не кешировать локаль глобально на сервере между пользователями.

Смена языка: сохранить через аутентифицированный BFF/API-путь; после успеха согласованно обновить cookie, клиентский provider и необходимые серверные фрагменты. Ошибка сохранения оставляет прежний язык и показывает локализованное сообщение. Не делать полный reload с потерей открытой формы; не remount-ить всё приложение через `key={locale}`. Сохранить черновики, фильтры, DnD-layout, активную страницу и query-данные. Для быстрых повторных переключений исключить запись устаревшего ответа (например, блокировкой выбора на время сохранения).

При новом входе/загрузке на другом устройстве используется последнее сохранённое значение. Мгновенная синхронизация открытых устройств не обязательна. Кеш предпочтений разделять по пользователю; если API отдаёт локализованное представление, такой кеш дополнительно разделять по локали.

## Представление и границы перевода

Меню языка располагается под темой в существующем AccountMenuDropdown. Названия языков — English, Русский, позднее Հայերեն, без флагов. Перевести aria-label, alt с системным текстом, tooltip, пустые/ошибочные состояния и сообщения сохранения. Сохранить доступность с клавиатуры и существующие компоненты UI.

Названия пользовательских задач, проектов, заметок, ссылок, имена сотрудников, сообщения и пользовательские справочники автоматически не переводить. Системные роли и статусы отображать по стабильному коду с безопасным исходным fallback; не переводить коды enum, разрешений, URL, идентификаторы и сохранённые ключи персонализации.

Даты, числа и относительное время форматировать с текущей локалью. Язык не меняет валюту, значения сумм, ISO-данные, календарную дату, первый день недели по бизнес-правилам или бизнес-часовой пояс. В частности, внутренний en-US в календарном алгоритме может быть частью извлечения даты: не заменять такие места механически. Менять форматирование представления, сохраняя семантику desk-line и Asia/Yerevan.

Ошибки: для затронутых сценариев использовать стабильные коды + параметры, локализованные поля валидации и общий безопасный fallback неизвестной ошибки. Не сопоставлять длинные английские сообщения строковыми заменами. Не показывать сырые серверные исключения. Внутренние диагностические логи сохраняют технические данные; пользовательский текст локализуется. Существующие коды ошибок сохраняются, новые поля вводятся совместимо. Полная миграция всех API-ошибок — отдельный этап.

Dashboard остаётся проекцией модулей: перевод не переносит бизнес-расчёты во frontend. Если projection содержит системный текст, использовать имеющийся стабильный тип/код либо добавить совместимые код/параметры, сохранив старый контракт до миграции потребителей. Пользовательский текст отделять явно.

Проверить кириллицу и армянский fallback-шрифт в текущей типографике. Не уменьшать весь интерфейс ради длинных слов: сначала краткие формулировки, переносы и гибкая ширина; критические действия должны читаться без обязательного tooltip.

## Начальный глоссарий EN/RU

| Понятие                  | Русская подпись            | Примечание                        |
| ------------------------ | -------------------------- | --------------------------------- |
| Dashboard                | Обзор                      | Главный Control Center            |
| Task / New task          | Задача / Новая задача      | Не смешивать с Project            |
| Project                  | Проект                     | Сохраняет значение Core Entities  |
| Product                  | Продукт                    | Отдельная сущность внутри проекта |
| Lead / Deal              | Лид / Сделка               | Разные стадии и сущности          |
| Meeting                  | Встреча                    | Сценарий календаря                |
| Expense                  | Расход                     | Не путать с Payment               |
| Payment / Invoice        | Платёж / Счёт              | Сохранять финансовые различия     |
| Appearance / Language    | Оформление / Язык          | Меню аккаунта                     |
| My Account / My wallet   | Мой аккаунт / Мой кошелёк  | Пока пункты меню                  |
| Save / Cancel / Sign Out | Сохранить / Отмена / Выйти | Общие действия                    |

Другие термины дополнять по модульному канону и контексту. Extension и другие специальные сущности не переименовывать произвольно.

## Следующие языки и этапы

Армянский: сначала 50–100 типичных строк, короткие и полные варианты спорных терминов, проверка носителем языка на desktop/mobile. Не утверждать машинный перевод как окончательный. После согласования добавить HY-каталоги, правила множественного числа и шрифт, пройти ту же приёмку и включить язык. Новый язык не должен требовать переписывания компонентов или изменения схемы БД; словари, enablement, языковая проверка и визуальная приёмка всё равно обязательны.

Дальнейшая русификация: аккаунт/кошелёк и ежедневные модули, затем остальные разделы; уведомления, письма, документы и внешняя коммуникация имеют собственную политику языка получателя и отдельный план. Язык внутреннего сотрудника не заменяет язык клиента.
