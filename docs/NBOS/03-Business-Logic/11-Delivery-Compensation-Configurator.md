# Delivery Compensation v2 — Каталог функций и Конфигуратор продукта

**Дата решения:** 2026-09-18. **Статус:** согласованный целевой бизнес-канон; реализация ещё не выполнена.

Документ фиксирует итог обсуждения с владельцем. Он имеет приоритет над более ранними описаниями расчёта delivery-бонусов, developer split 70/30 и показа Bonus внутри Delivery. Остальные правила Sales, оклада, KPI, funding, releases, payroll и фактических выплат сохраняются, кроме отдельно указанного добавления `From = Network`.

Вход в пакет реализации: [README](../../implementation/delivery-compensation/README.md). UI: [спецификация экранов](../05-UI-Specifications/15-Delivery-Function-Catalog-and-Configurator.md).

## 1. Цель и границы

Убрать регулярное ручное назначение суммы каждому исполнителю каждого продукта. PM описывает работу и назначает исполнителей; система использует утверждённые нормативы; сотрудник видит собственный плановый бонус в кошельке с начала Development.

В scope:

- одноразовый delivery-цикл Product и Extension, включая разовую SEO-настройку;
- роли Backend, Frontend, PM, Designer, QA, Technical Specialist;
- базовая комплектация, крупные дополнительные функции, инструкции и вложения;
- версия норматива и тарифов, смена scope и исполнителей;
- создание плановых бонусов, интеграция с существующими Finance/Wallet;
- новый CRM `From = Network` со стартовыми правилами Client.

Вне scope этой реализации:

- ежемесячные SEO, maintenance и другие циклические работы;
- новый KPI для delivery, новая модель оклада, налоги, изменение cap/carry-over;
- автоматическая оценка задач ИИ, автоматическое обучение тарифов;
- отдельный процесс R&D и обязательная премия за автоматизацию;
- публичные units, персональные тарифы по грейду/сотруднику;
- калькулятор себестоимости, сроков и рекомендованной цены Seller: отдельный следующий проект;
- связь функции с Credential: будущая возможность, без хранения секретов в инструкции;
- production deployment, production migrations и автоматическая миграция старых бонусов.

Клиент может платить за разовую разработку по подписке: это НЕ превращает delivery-бонус в ежемесячный. Funding использует существующие оплаты заказа.

## 2. Термины

| Термин                | Значение                                                                                                                                                                                 |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Каталог функций       | Общая библиотека крупных повторяемых работ, инструкций и закрытых нормативов                                                                                                             |
| Конфигуратор продукта | Выбор параметров и функций конкретного Product/Extension                                                                                                                                 |
| Базовая комплектация  | Понятный объём стандартных работ и независимые units каждой роли                                                                                                                         |
| Функция               | Крупный блок: банковская оплата, складская интеграция, миграция и т. п.                                                                                                                  |
| Unit                  | Внутренняя нормативная единица бонуса; не час, не календарный день и не себестоимость                                                                                                    |
| Тариф роли            | Денежная стоимость unit для одной роли, одинаковая для всех сотрудников этой роли                                                                                                        |
| Цена продажи          | Ставка AMD за unit всегда на версии карточки (функция / градация / ядро); нет ставки — нет суммы. Не ось бонуса: `units × ставка продажи` — сумма клиенту, себестоимость в неё не входит |
| План бонусов          | Зафиксированный расчёт по scope, версиям правил, ролям и получателям                                                                                                                     |
| Изменение плана       | Новая ревизия, сохраняющая предыдущие договорённости и историю разницы                                                                                                                   |

Task/checklist и функция каталога — разные сущности. Не каждая задача даёт отдельный бонус. Мелкие и уникальные работы могут входить в уже согласованную базу. Их выполнение не требует обращения к Owner за units.

## 3. Параметры продукта и база

Конфигуратор использует существующие `Product.productType` и `productCategory`, не вводит заменяющую их классификацию Project. `Product.productPlatform` (`WEB` / `APP` / `DESKTOP`) — атрибут сделки и карточки продукта: где продукт работает. Это не ось расчёта. Одинаковый функционал стоит одинаково на любой платформе; платформа не входит в ключ базового профиля. Поле есть только у Code (все три значения) и у WordPress/Shopify (`WEB`). У Marketing платформы нет — в БД `NULL`, поле не показывают.

На Code список видов для нового выбора зависит от платформы (решения 1.22–1.23). Web — самый широкий список, App уже, Desktop самый узкий. Сайты предлагаются только на WEB. POS — APP и DESKTOP. Магазин, маркетплейс, порталы и LMS не предлагаются на DESKTOP. `WEB_APP` — кастомная система, доступна на WEB, APP и DESKTOP. `BOS` — общая операционка компании; `INDUSTRY_OPERATIONS_SYSTEM` — узкий отраслевой процесс. `MOBILE_APP` и `SAAS` остаются в enum для legacy-карточек и не предлагаются в новом выборе. WordPress — WEB: визитка, корпоративный, лендинг, каталог, блог, магазин. Shopify — `ECOMMERCE`, только WEB. Marketing — без платформы, виды без изменений. Смена платформы сбрасывает вид, если он недопустим. SEND_OFFER и create/update Product/Deal отклоняют недопустимую пару.

Оси «основа реализации», «три режима дизайна» и «AI-reviewer» **сняты 2026-09-21 (решение 1.21).** Они не участвуют в выборе, матчинге ядра и readiness. Стандартный дизайн входит в ядро. Колонки в БД остаются и пишутся заморозкой `FROM_SCRATCH` / `AI_DESIGN` / `false`.

Размер конфигуратора (`SMALL` / `CLASSIC` / …) **снят 2026-09-21.** Один вид — одно ядро и одна цена каркаса. Комплектация — именованный помощник галочек в конструкторе, не ось нормы и не множитель units. Объём каталога (500 vs 500 000 товаров) живёт градациями конкретных карточек (импорт, поиск, нагрузка), не пятью версиями ядра.

У доработки нет своего ядра и нет `Extension.size`. Карточка Extension в Delivery и в сделке остаётся. Правило чеклиста этапа для доработки не зависит от размера и применяется ко всякой доработке этого этапа.

Owner/CEO настраивает одно ядро на каждый вид, который можно выбрать для нового продукта. Список норм показывает каждый такой вид сразу: пустая карточка значит, что норма ещё не задана. Скрытые legacy-виды (`MOBILE_APP`, `SAAS`) в списке нет. Повторное сохранение обновляет открытый черновик или создаёт следующую версию того же ядра, а не второй profile key на тот же вид. Ядро содержит по каждой роли одно из трёх положений: роль нужна (слот обязателен, включая явный 0), роль если есть (слот можно оставить пустым, назначенный человек получает units), роль не нужна. Нельзя выдавать скрытый default 0 для ненастроенного ядра. Вид без опубликованного ядра показывает «норматив не настроен».

Сложность/переиспользование уже отражены в выбранном профиле. Второй общий коэффициент зрелости поверх уменьшенных units не применяется. Скорость конкретного сотрудника не уменьшает согласованный бонус. Повторяемая работа может получить новую версию 50 → 5 → 0 units после автоматизации; история проектов сохраняет прежнюю версию.

## 4. Дополнительные функции и включение в базу

Карточка функции содержит отдельные units каждой затронутой роли. Это не процент от общей суммы заказа. Не нужно дробить каталог до кнопок, небольших исправлений и обычных задач.

В блоке «Входит в базу для…» Owner/CEO выбирает ядра по виду продукта. Сохраняются однозначные связи с ядром этого вида. Никаких неявных конкурирующих wildcard-правил с неясным приоритетом.

Для конкретной конфигурации:

1. Функция входит в выбранную базу → автоматически активна, badge «Включено в базу», добавочные units равны 0. Её работа уже оплачена базовыми units соответствующих ролей.
2. Функция не входит в базу → доступна через «+ Добавить», её units прибавляются по ролям.
3. Один и тот же экземпляр работы нельзя добавить дважды. Независимые интеграции разных провайдеров могут быть разными явно названными функциями.
4. Выбор функции означает scope, а не завершение работы. Статус выполнения и инструкция независимы от selection.

Функция, включённая в базу, в v1 не выключается обычным toggle с автоматической скидкой. Иную комплектацию extra-функций продавец собирает в конструкторе сделки (клик по именованному комплекту заменяет набор, затем можно снять и добавить руками). Комплект не меняет ядро и не делает функции бесплатными. Не превращать каждую включённую функцию в отдельную часть базовой цены: базовый бонус неделим на такие автоматические компоненты.

Если каталог/состав базового профиля изменён, старый продукт не получает новые функции и не меняет цену сам. В Starting PM может явно обновить черновик до актуальной версии. После Development старые строки заморожены; для новых дополнительных функций используется актуальная опубликованная версия и актуальные тарифы на дату изменения. Факт «входит в базу» для добавляемой функции определяется замороженным базовым профилем текущего продукта.

## 5. Расчёт и точность

Для роли `r`:

```text
BaseBonus(r) = BaseUnits(r) × RoleRate(r)
ExtraBonus(f, r) = ExtraUnits(f, r) × RoleRate(r)
RoleBonus(r) = BaseBonus(r) + сумма выбранных ExtraBonus(f, r)
EmployeeBonus(e) = сумма принадлежащих e долей RoleBonus
DeliveryPool = сумма EmployeeBonus всех участников
```

Каждый компонент хранит собственный snapshot норматива и тарифа. При позднем добавлении функции её новый тариф не применяется к старой базе/функциям. Итог поэтому является суммой компонентных денежных сумм, а не суммой старых и новых units, умноженной на один сегодняшний тариф.

- В v1 расчёт delivery ведётся в AMD; не выполнять скрытую конвертацию валют. Несовместимый валютный путь должен иметь явный blocker до включения в payroll.
- Units и тарифы — неотрицательные Decimal, деньги округляются до 2 знаков ROUND_HALF_UP на компонент/роль.
- Распределение округляет доли с сохранением полной исходной суммы; последний получатель получает детерминированный остаток копеек. Это техническое округление, не автоматический выбор процента участия.
- `null` означает «не настроено», `0` — явное решение о нулевом начислении. Публикация нулевого норматива требует явного подтверждения Owner.
- RoleRate различается по ролям, но не зависит от человека, его оклада или грейда.
- Один сотрудник в двух ролях получает две части. Новый расчёт не вызывает старый developer split 70/30 и не превращает две роли одного человека в одну.
- Ненужная роль явно исключена профилем, её деньги не перераспределяются. Отсутствие назначенного человека само по себе не означает исключение роли.

Тестовый пример, НЕ коммерческий seed: база Backend 100 × 1 000 = 100 000 AMD; Frontend 50 × 800 = 40 000. Bank уже в базе → добавка 0. Warehouse: Backend 10 × 1 000 + Frontend 5 × 800 = 14 000. Всего 154 000. Если оба слота занимает один человек, он получает 154 000, без вторичного 70/30.

## 6. Дизайн

Отдельных режимов дизайна нет. Стандартный дизайн — часть ядра вида. Дополнительная дизайнерская работа, если её продают отдельно, — карточка каталога, не ось профиля. Назначение Designer на карточке не меняет units и не требует reviewer-флага.

## 7. Работа с неизвестными и разовыми задачами

Не создавать обязательную «неоценённую функцию» при каждой новой задаче. Команда выполняет работу в обычных задачах. Owner/CEO при необходимости позже:

- создаёт повторяемую функцию, назначает units и публикует её; PM выбирает её для текущего активного продукта;
- либо использует существующий персональный ручной бонус без добавления функции в каталог;
- либо оставляет работу в текущей базе без дополнительного начисления.

Создание функции после выполнения конкретной работы допустимо, пока Product/Extension находится в активном delivery-цикле. Это не означает ожидание завершения всего продукта. Для завершённого продукта нельзя снова запускать конфигуратор ради начисления: использовать существующую финансовую корректировку или новый Extension.

Стартовые функции без units — черновики каталога, не активные оплачиваемые selections. Они не блокируют разработку, если не включены в продукт. В Product нет placeholder-обязанности получить оценку для каждой уникальной задачи.

Ручной бонус не поглощается автоматически новым расчётом. Если он уже оплатил ту же работу, перед добавлением функции необходимо разрешить дублирование в Finance с явной связью и reason; система предупреждает по связанным записям, но не угадывает совпадение по тексту.

## 8. Starting → Development

В Starting PM назначает команду и подтверждает параметры/функции. Сохранение черновика не создаёт `BonusEntry`, payroll, выплаты или employee wallet income.

Перед первым входом в Development для новой модели обязательны:

- корректная связь с конкретным Order/Product либо Order/Extension;
- для продукта — опубликованное ядро этого вида; у доработки своего ядра нет, и план на входе в Development строится только из выбранных дополнительных функций;
- тарифы всех оплачиваемых ролей;
- опубликованные и оценённые выбранные дополнительные функции;
- проверенная конфигурация без неподтверждённых изменений;
- действующие исполнители требуемых ролей, отсутствие двусмысленных назначений;
- разрешение actor и все существующие delivery stage gates.

Переход и формирование плана должны быть одной атомарной командой. Система фиксирует scope, включённость в базу, финансовые версии, получателей; материализует плановые `BonusEntry`; показывает персональные суммы в кошельке как прогноз/бонусы в работе. Это не разрешение немедленно выплатить деньги.

Откат стадии, pause/resume, retry, одновременные клики и повторный вход в Development не создают второй исходный бонус. Development без успешно созданного обязательного плана для новой модели недопустим.

## 9. Изменение scope после старта

PM с правом конфигурации может добавить опубликованную функцию без обращения к Owner за её оценкой. Он видит изменение объёма, но не units/суммы. Изменение сохраняется явно, с reason после старта; сервер создаёт следующую ревизию и обновляет только затронутые бонусы. В кошельке получатель видит свою денежную разницу и причину.

Для удаления дополнительной функции или отмены продукта сохраняется бонус за принятую выполненную работу. Невыполненную часть можно убрать. PM подтверждает факт/долю выполненного без default-процента; не меняет units, тарифы и денежную формулу. Финансовые ограничения уже включённых в payroll/выплаченных сумм не обходятся.

Переклассификация базового профиля/режима дизайна после Development — явно выделенная корректировка с просмотром технического diff, reason, новыми версиями и сохранением выполненного; не silent repricing всего плана. Если требуется денежное исключение, оно проводится существующим permissioned Finance-flow. Обычные добавления опубликованных функций не требуют CEO approval.

После Done/Cancelled рабочая конфигурация read-only. Отмена не равна Done: сохранённые начисления за принятую часть не должны автоматически проходить funding-gate как за сданный продукт. Их выпуск — через существующее разрешённое ручное действие Finance с reason.

## 10. Смена исполнителя

Точка входа: изменение участника в Delivery sheet или Product page. Оба места вызывают один серверный процесс. Extension имеет собственное назначение ролей для своего плана; смена команды родительского Product не переписывает бонусы Extension автоматически.

- До плана в Starting — обычная замена.
- После плана — обязательное окно распределения по базовой части и затронутым дополнительным функциям.
- Проценты/доли ВСЕГДА вводятся человеком; поля пустые, Save заблокирован до заполнения. Не подставлять 0/100, 50/50 или «рекомендуемую» долю даже при предположении, что работа не начата.
- Сумма долей по каждой распределяемой части = 100%; ввод означает долю остатка текущего исполнителя, если предыдущие замены уже сохранили доли других людей. UI явно показывает предмет деления.
- Базу не требуется раскладывать по каждой встроенной функции. Её доля задаётся вручную. Дополнительные функции — отдельными строками.
- PM видит имена, роль, названия работ, доли и reason; суммы и units остаются закрытыми.
- Общая стоимость работы не возрастает от замены. Сохраняются история прежних получателей, уже выполненное, releases, payroll и выплаты.
- Если изменение пытается передать уже выплаченное или зарезервированное для payroll, сервер отказывает в таком финансовом изменении с безопасным кодом для PM; вопрос решается в Finance, не удалением ledger.

## 11. Кошелёк и существующая финансовая цепочка

Product/Delivery для всех рабочих ролей — scope, исполнители, задачи, инструкции. Новая вкладка «Функции» заменяет старую Bonus-вкладку; не добавлять суммы даже если Owner открыл рабочую карточку. Управление расчётом — в каталоге/Compensation, просмотр денег — Wallet/Finance.

Сотрудник в кошельке видит только своё: Product/Extension, название работ/причину изменения, плановую сумму, включённую в payroll, выплаченную и остаток. Units, ставки и чужие доли денег не возвращаются его API. Детализация units в будущем — отдельное решение.

Сохраняется цепочка:

```text
План из конфигуратора → BonusEntry → funding/eligibility → BonusRelease
→ PayrollRun / SalaryLine → Expense → ExpensePayment → Wallet projection
```

Нового баланса кошелька и второго payment ledger нет. `ProductBonusPool` продолжает считать фонд конкретного order. Плановый bonus не должен дважды суммироваться вместе со своей материализованной BonusEntry. Существующие early/extra/over-funding/correction, cap и carry-over остаются; sales KPI не применяется к delivery по новой самодельной формуле.

Период заработанного бонуса не равен дате создания прогноза в Development. Совместимость `earnedPeriod`, месячного eligibility и позднего финансирования обязательна; технический контракт и отдельные regression cases описаны в пакете реализации.

## 12. Полномочия и инструкции

- Только CEO/Owner настраивают/публикуют units, базовые профили, тарифы, included-in-base и их финансовые версии. Finance не получает эти права автоматически.
- Назначенные редакторы знаний (PM/специалисты) могут обновлять инструкции без права менять расчёт. Финансовые и контентные версии независимы.
- PM/уполномоченный actor выбирает опубликованные функции и управляет своей конфигурацией в границах доступа к Product.
- Developer читает разрешённые инструкции. Наличие ссылки не выдаёт доступ к чужому проекту/файлу.
- Seller может читать каталог и, при отдельном праве на соответствующий draft, готовить scope. Не расширять ему доступ к delivery/зарплатам автоматически и не строить калькулятор оффера сейчас.

Карточка функции одна; «Инструкция» доступна команде, «Расчёт» только Owner/CEO. Изменение инструкции не меняет финансовый snapshot. Общая инструкция и локальные заметки продукта хранятся отдельно. Ссылки и изображения используют существующий защищённый файловый механизм. Raw credentials в тексте не допускаются.

## 13. Network — отдельное ограниченное изменение Sales

Добавить верхнеуровневый `LeadSourceEnum.NETWORK` с label Network. Это не существующий Sales channel `NETWORKING`. Исторические `SALES + NETWORKING` не переклассифицируются автоматически.

Стартовая политика «как Client»:

| Payment model            | Seller | Assistant |
| ------------------------ | -----: | --------: |
| CLASSIC                  |     4% |        1% |
| SUBSCRIPTION_FIRST_MONTH |    40% |       10% |
| SUBSCRIPTION_RECURRING   |     0% |        0% |

«5%» означает суммарно 4% + 1% для Classic. Network получает отдельные редактируемые policy rows; live-связи с Client нет. Перед seed проверить текущие Client rates: если они отличаются от зафиксированного baseline, не перетирать Client и не копировать их молча; отметить расхождение для Owner. Изменяется только новый source, старые источники и Seller engine сохраняются.

## 14. Legacy, начальные данные и критерий готовности

Новые продукты после включения модели используют её по умолчанию. Существующие — explicit legacy/skip; чтение, повторное открытие и движение старой карточки не создают новое обязательство сами по себе. Owner может отдельно инициировать adoption для выбранной активной карточки с preview и проверкой существующих начислений.

Каталог можно seed-ить названиями, категориями и инструкциями без финансовых величин. Коммерческие units, тарифы и размеры базовых бонусов пользователь ещё не предоставил: они не должны выдумываться как «согласованные». Полный код реализуется и тестируется на явно тестовых fixtures; перед реальным запуском Owner публикует рабочие нормативы через готовый UI.

Модель готова, когда обычный проект проходит Starting → Development → изменение scope/команды → Done → существующий Finance/Wallet без ручного определения денег, без утечки units и без двойного начисления. Подробные сценарии, фазы и факт выполнения — в [пакете реализации](../../implementation/delivery-compensation/README.md).
