# Решения заказчика: Product, Extension, Maintenance, Hub

**Назначение:** зафиксировать договорённости из переписки и то, что **намеренно отложено**. Канон для разработки и дальнейших правок `docs/NBOS`.

**Исходник-архив:** `docs/archive/New-Description/00-Open-Questions-and-Decisions.md`.

**Связанные документы:** `01-Platform-Overview/03-Core-Entities-and-Data-Model.md` § 1.1; `02-Modules/02-Projects-Hub/05-Product-Centric-Navigation.md`.

---

## Принятые решения

### Один проект — несколько продуктов

- В одном **Project** может быть **несколько** продуктовых линий.
- На каждый такой поток: **отдельная Deal** (тип PRODUCT), **отдельный Order**, **отдельная карточка на Delivery Board**; далее **отдельные** истории по maintenance и остальному — по тем же правилам разделения.

### Delivery Board: Product и Extension

- На Delivery Board попадают и **Product**, и **Extension** (отдельные карточки/линии).
- У **Product** и у **Extension** внутри — **разные наборы полей** и **разное визуальное оформление** карточки.

### Бонусы команды: Product и Extension

- **Сейчас:** за каждый создаваемый **Product** и за каждый создаваемый **Extension** команда получает **свои бонусы** (учёт отдельно).
- **Возможное будущее:** правила могут измениться; возможны **стандартные типы extension** в системе.
- **Возможное будущее:** часть работ — «мини-extension» (пара часов задач, без полноценной delivery-линии); даже при полной оплате через Deal/Order прохождение может быть **минимальным по времени**. Сейчас так **не** делаем; при проектировании системы **можно заложить** учёт таких сценариев.

### Extension: связь с продуктами (MVP)

- Если связь **с несколькими продуктами** заметно сложнее в реализации, на первом этапе — **самая простая версия**: **минимум одна связь с одним Product** (если множественный выбор откладывается).
- В перспективе возможны: множественный выбор продуктов **или** связь **только с Project** (без продукта) — до уточнения по сложности и продуктовой необходимости.

### Deal Type = MAINTENANCE и кейс «только обслуживание»

- Для сценария **maintenance-only** (клиент пришёл только на обслуживание, без нашей предыдущей разработки в NBOS): должны появиться **Project**, **Product** и `Subscription` (`type = MAINTENANCE_ONLY`, `status` ∈ { `PENDING`, `ACTIVE` }) — не оставлять продукт «в воздухе» без объекта в проекте. Отдельного статуса/флага обслуживания на `Product` нет.
- Для обычного сценария после собственной разработки NBOS: maintenance deal создаётся как связанная коммерческая карточка вокруг уже существующего `Project` и `Product`.
- После основного `PRODUCT -> Deal Won` система может автоматически создать подготовленную `MAINTENANCE` deal card.
- В этой карточке поле `deadline` трактуется как `planned maintenance start date`.

## Закрыто: признак «продукт на maintenance»

**Решение (2026-08-13):** отдельного поля на `Product` нет и не будет. Ручного флага (`maintenanceMode` и аналоги) нет. Сущности `Maintenance` в БД нет: Maintenance — **view**, не сущность.

Продукт на обслуживании, если у него есть `Subscription` с:

- `type` ∈ { `MAINTENANCE_ONLY`, `DEV_AND_MAINTENANCE` };
- `status` ∈ { `PENDING`, `ACTIVE` }.

`PENDING` = обслуживание продано, но ещё не стартовало (создаётся при Deal Won для `Deal.type = MAINTENANCE`, `billingStartDate` = `Deal.maintenanceStartAt`). Статусы `ON_HOLD` / `CANCELLED` / `COMPLETED` = «maintenance отключён», работы не ведутся.

Исключения (внутренний продукт, спецпроект, бесплатное ведение) оформляются той же подпиской с `baseMonthlyAmount = 0` и `type = MAINTENANCE_ONLY`. Новых полей не добавлять.

**Доска Maintenance** — UI-view («какие продукты на обслуживании»), не отдельная таблица. Специалисты Support / maintenance работают с продуктами, у которых есть такая подписка.

Проектные hub views (`Development` / `Maintenance` / `Closed`) считаются из детей; у `Project` нет lifecycle-статуса. Формулы: `02-Modules/02-Projects-Hub/01-Project-Hub-Overview.md` §8.

## Открытые вопросы

### MAINTENANCE: поля Deal и автосоздание Product

- Для обычного сценария с уже существующим продуктом `MAINTENANCE` deal не создаёт новый продукт.
- Карточка maintenance связывается с существующим `Project` и `Product`.
- Из основного Deal / Product подставляются стабильные поля; коммерчески переменные поля заполняются Seller отдельно.
