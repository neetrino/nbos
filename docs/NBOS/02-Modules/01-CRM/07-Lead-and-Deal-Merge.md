# Объединение Lead и Deal; дедуп на входе

> NBOS Platform — идентичность человека, attach входящих и merge карточек
>
> **Статус:** канон (2026-08-19). Runtime: Phase 1–2 shipped (`06-Implementation-Status.md`). ATS exact-phone attach kept. Deal merge (Phase 4) not shipped.
>
> Связанный канон: `01-CRM-Overview.md`, `02-Lead-Pipeline.md`, `03-Deal-Pipeline.md`, `../03-Clients/02-Contacts.md` (Contact merge), `../../03-Business-Logic/09-Entity-Lifecycle-Standard.md` (Profile A Trash).

## 1. Назначение

Один человек не должен получать две карточки Lead из‑за двух каналов одного запроса. Два разных запроса того же человека — две карточки Lead на одном Contact. Две сделки на одном Contact часто корректны. Merge Deal — только для случайного дубля **одной и той же продажи**.

Канон описывает **полную модель сейчас**. Код — позже, по фазам § 11. Deal merge задокументирован как контракт, не как следующий MVP-срез.

## 2. Слои

| Слой        | Сущность                                             | Смысл                                                                         | Объединение                                             |
| ----------- | ---------------------------------------------------- | ----------------------------------------------------------------------------- | ------------------------------------------------------- |
| **Contact** | кто (человек)                                        | Несколько Lead могут быть на одном Contact                                    | Уже в Clients (`02-Contacts.md` §6–7). Не переписывать. |
| **Lead**    | одно входящее обращение / квалификация на Lead Board | Одна карточка на один запрос                                                  | Wizard § 6                                              |
| **Deal**    | одна коммерческая возможность                        | PRODUCT + MAINTENANCE, сайт + приложение, Extension — часто **разные** сделки | Строгий merge § 7; по умолчанию не объединять           |
| **Канал**   | Instagram, звонок, форма, WhatsApp                   | История на карточке                                                           | Не вторая карточка Lead/Deal                            |

**Contact merge ≠ Lead merge.** Contact = кто. Lead = рабочий элемент доски. Свести два Contact недостаточно, если на доске остались два обращения об одном запросе.

## 3. Когда объединять и когда нет

| Ситуация                                                                          | Решение                                                                    |
| --------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| Тот же человек + тот же запрос + два входа (Instagram DM, затем звонок)           | **Один Lead.** Второй вход — канал / активность.                           |
| Тот же человек + два разных запроса (сайт сейчас, приложение позже)               | **Два Lead**, один Contact. Не объединять.                                 |
| Две сделки на одном Contact (PRODUCT + MAINTENANCE, сайт + приложение, Extension) | Часто **корректно**. Связанные сделки показать; не сливать.                |
| Случайный дубль **одной** продажи (две карточки про тот же заказ)                 | Deal merge только при стражах § 7; иначе закрыть дубль как Failed / Trash. |

## 4. Проблема runtime (зачем канон)

Сегодня в CRM-каноне не было Lead/Deal merge. Факт в коде:

- Meta ingest создаёт Lead на каждый Instagram-диалог (`MetaConversation.leadId` — 1:1). Телефона обычно нет.
- ATS inbound ищет открытый Lead **только по телефону**; иначе создаёт новый Lead.
- Итог: Instagram + позже звонок = две карточки Lead.
- `Deal.leadId` уникален: один Deal на один Lead.

Prevention (слой 1) даёт наибольший ROI: не плодить вторую карточку. Wizard (слой 2) чинит уже созданные дубли.

## 5. Слой 1 — Prevention (intake attach)

На создании Lead (ручное, Instagram, форма сайта, ATS-звонок):

1. Искать открытый Lead / Contact по телефону, email, Instagram-идентичности.
2. Найден открытый Lead → **привязать** разговор / звонок к нему. **Не** создавать второй Lead.
3. У человека уже есть открытый Deal → **предупредить**. Второй Lead молча не создавать.
4. Ручное создание: жёлтый баннер с кандидатами — открыть / привязать / всё равно создать.
5. Seller **добавляет телефон** к Instagram-Lead → найти ATS/другие Lead с этим телефоном и **предложить merge**. Авто-merge по неуверенной идентичности запрещён.
6. ATS **оставляет** авто-attach, если телефон **точно** совпал с открытым не-SQL Lead (уже в runtime).
7. Кросс-канал **без** общего идентификатора — не авто-merge и не авто-attach.

**Открытый Lead** для attach: не SQL, не поглощён (`mergedIntoId` пуст), не в Trash. **SPAM** — не цель авто-attach (в ручном баннере можно показать как кандидата). **Frozen** — открытый для **точного** совпадения телефона/email (как ATS non-SQL).

## 6. Слой 2 — Lead merge (исправление)

Wizard: выбрать **survivor** и **absorbed**.

| Тема                   | Правило                                                                                                                                              |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| Конфликт полей         | Пользователь выбирает: имя, телефон, email, From/Where, assignee. Пустые поля survivor можно заполнить из absorbed.                                  |
| Стадия                 | По умолчанию более продвинутая; пользователь может переопределить. On Hold не «продвинутее» активной стадии. Frozen/SPAM не цель стадии survivor.    |
| Всегда переносится     | Заметки (append), события ATS, Meta-разговор, доп. контакты, файлы/ссылки.                                                                           |
| Marketing / From-Where | Не затирать молча. First-touch = более ранний Lead (`createdAt`). Второй источник — доп. канал / событие таймлайна (CPL/ROI).                        |
| Поглощённый Lead       | Указатель `mergedIntoId` + Profile A **Trash**. Не hard delete. Не стадия `MERGED`. Код карточки виден в audit.                                      |
| Доска                  | Survivor остаётся в своей колонке (или в выбранной стадии). Absorbed уходит с доски через Trash + указатель.                                         |
| Meta 1:1               | Если у обоих есть Meta-разговор: survivor забирает разговор; у absorbed связь **снимается** (unlink). Второй диалог не хранится как второй `leadId`. |

**Блокировать (не молчаливый merge):**

- Один уже SQL / сконвертирован в Deal — путь Deal или оставить исходный Lead.
- У обоих есть Deal — это задача слоя 3, не Lead merge.
- Неуверенная идентичность — только предложение, не авто.

## 7. Слой 3 — Deal merge (строгий)

**По умолчанию не объединять.** Показать связанные сделки. Предпочтительнее закрыть дубль как **Failed** / **Trash**, чем сливать деньги и статусы.

Разрешить merge только если **все** условия истинны:

- обе сделки **OPEN** (не WON);
- нет Order, нет оплаченного Invoice, нет проведённого sales bonus;
- тот же коммерческий предмет — **явное подтверждение** пользователя;
- компания пустая или одна и та же.

**Блок / жёсткое предупреждение:**

| Ситуация                                         | Действие                                                           |
| ------------------------------------------------ | ------------------------------------------------------------------ |
| Любая сторона WON (Project / Order / handoff)    | Блок. Не разрушать finance/Won.                                    |
| Разный Deal Type (PRODUCT vs MAINTENANCE и т.д.) | Блок.                                                              |
| Суммы                                            | Не складывать автоматически. Пользователь выбирает сумму survivor. |
| FAILED + открытая                                | Это «закрыть дубль», не денежный merge.                            |

Если merge всё же идёт: стадия — более поздняя (или выбор); amount / type / offer / contract — ручной выбор; файлы offer/contract в Drive перепривязать к survivor; survivor **сохраняет свой** `leadId`; Lead absorbed-сделки не сливать молча. Поглощённый Deal → Trash + `mergedIntoId`.

## 8. UX

Действие на шите Lead/Deal: **Объединить** → поиск другой карточки → survivor → таблица конфликтов → превью что переносится → подтверждение.

Жёлтый баннер, если телефон/email совпал с другим открытым Lead/Deal.

Отдельный admin-only экран **не** единственный путь.

## 9. Права

| Роль              | Merge Lead / Deal                                                                                                         |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------- |
| **Seller**        | Да, если **обе** карточки ему назначены / он ответственный (`assignedTo` на Lead, `sellerId` на Deal). Иначе — эскалация. |
| **Head of Sales** | Любые карточки                                                                                                            |
| **CEO**           | Любые карточки                                                                                                            |
| **Marketing**     | Только чтение. Merge нет.                                                                                                 |
| Остальные         | Нет                                                                                                                       |

Права на Contact merge — в Clients; они не дают права сливать Lead/Deal.

## 10. Audit и указатель

Фиксировать: кто, когда, from → to (absorbed → survivor), выбранные значения конфликтующих полей, факт unlink Meta-разговора.

Канонический указатель поглощения — **`mergedIntoId`**. Имя колонки в Prisma может отличаться; смысл один. Не вводить стадию `MERGED`. Не подменять merge hard delete.

Восстановление поглощённой карточки из Trash **без** отдельного un-merge блокируется (иначе снова две активные карточки). Un-merge в этом каноне не описан.

## 12. Никогда

- Авто-merge без подтверждения (исключение: уже существующий ATS attach по **точному** телефону к открытому не-SQL Lead).
- Hard-delete поглощённой карточки.
- Авто-сложение двух сумм Deal.
- Считать Contact merge заменой Lead merge.
- Оставить только «связанные карточки» без реального Lead merge, если это один запрос и два входа.
- Новая колонка Kanban `MERGED` или терминальная стадия `MERGED`.
- Молчаливый merge SQL/Won/Order/оплаченного Invoice / проведённого бонуса.
- Авто-attach кросс-канал без общего идентификатора.
