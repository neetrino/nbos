# Домены: покупка, подключение и операционная работа

**Статус канона:** утверждённая целевая модель; этот документ не является доказательством готовности в продукте.
**Код (2026-09-17):** частичная реализация в рабочей ветке — [факт по коду](../../../implementation/CLIENT-SERVICES-IMPLEMENTATION-PLAN.md#9-фактический-статус-кода-2026-09-17). Production-схема этого среза не применялась.
**Решение:** согласовано с владельцем NBOS, зафиксировано 2026-09-17.
**Область:** домены Client Services, Product / Delivery, Invoice, Expense, Tasks и Credentials.

Этот документ фиксирует последние согласованные решения. Для доменного процесса он уточняет и заменяет прежние последовательности из [общего канона Client Services](07-Domains-Hosting-Licenses.md). Другие типы сервисов не переводятся на новый процесс автоматически.

План работ и критерии приёмки: [план реализации](../../../implementation/CLIENT-SERVICES-IMPLEMENTATION-PLAN.md). Передача исполнителю: [Cursor handoff](../../../implementation/CLIENT-SERVICES-CURSOR-HANDOFF.md).

## 1. Принятые границы

- Project сохраняет бизнес-контекст, Product — рабочий контекст. В текущем релизе покупка всегда имеет Product; клиент и Project определяются из него.
- Один домен — отдельный Client Service. Используется существующая связанная Domain-модель без второго независимого процесса.
- Один аккаунт регистратора — один Credential; несколько доменов и Products могут использовать его по ссылке. Связь не расширяет права на секрет.
- Глобальный реестр Client Services остаётся в Finance. Новый top-level модуль не создаётся.
- Сотрудник открывает ту же карточку сервиса из Product, Delivery или связанной Task, в пределах своих разрешений.
- Один бизнес-action создаёт необходимые связи автоматически; сотрудники не синхронизируют модули вручную.
- Процесс допускает разный порядок действий. Сохранение неполных данных разрешено. Неизвестная цена не блокирует запуск потребности из Product.
- Реализованная проверка RDAP/WHOIS сохраняется; новый lookup-сервис не строится.
- Новые сценарии не расширяют автоматически получателей, каналы и правила финансовых уведомлений.

### Вне текущего объёма

Покупка до появления Product; выбор Deal/Client в доменной форме; автоматический перенос с Deal; общий Invoice на несколько сервисов; отдельный workflow engine; универсальная ProviderAccount-сущность; структурированный RegistrantProfile; автоматическая оплата через сайты регистраторов; специальный процесс возврата при отмене покупки.

Редкие покупки без Product и отказы после оплаты обрабатываются вручную существующими средствами. Не создавать фиктивный Product и не реализовывать дополнительный UI для этих исключений.

Отдельная сущность ServiceOperation / DomainPurchaseCase обсуждалась, но обязательной частью реализации не утверждена. До изменения схемы проверить, достаточно ли существующих связей Invoice, Expense, Client Service и минимального устойчивого идентификатора операции. Защита от дублей обязательна независимо от выбранного хранения.

## 2. Два входа в один процесс

```text
Delivery / Product → Купить / подключить домен ─┐
                                               ├→ Client Service → связанные действия
Invoice Board → Создать → Покупка домена ───────┘
```

### Product и Delivery

Компактный элемент в шапке открытой карточки Product на Delivery и на полной странице Product, справа, перед меню действий и над вкладками. На узком экране переносится под название внутри шапки. Отдельного постоянного блока и кнопки на маленькой kanban-карточке нет.

| Состояние                                 | Представление                                   |
| ----------------------------------------- | ----------------------------------------------- |
| Доменных записей нет                      | Купить / подключить домен                       |
| Покупка идёт                              | Домен · Ожидает оплаты / Подготовка             |
| Куплен, ещё не подключён                  | example.am · Куплен                             |
| Подключение с нашим доступом подтверждено | example.am · Подключён                          |
| Клиент управляет подключением             | example.am · Через DNS клиента                  |
| Несколько доменов                         | Домены: N; при необходимости — Требует действия |

Цвет дополняет текст, а не заменяет его. Завершённое состояние спокойное. Нажатие открывает список доменов и «+ Купить / подключить ещё». Новая покупка доступна во время разработки и через месяцы после закрытия delivery: Product не возвращается в активную доску.

### Invoice Board

В создании Invoice два пользовательских пути: существующий свободный счёт и «Покупка домена». Доменная форма использует один обычный dropdown Products, без вкладок Deal/Client и без дополнительного вопроса «До начала проекта?».

Для выпуска Invoice нужны Product, доменное имя, подтверждённая клиентская сумма и существующие обязательные реквизиты Finance. Неизвестные цена и провайдер уточняются через процесс из Product, а не обходятся нулевым счётом.

Создание доменного Invoice создаёт или переиспользует Client Service сразу в состоянии планируемой покупки. Нельзя ждать оплаты, чтобы впервые сохранить домен. Если PM уже начал покупку, Invoice связывается с существующей открытой покупкой; повторный сервис и счёт не создаются.

## 3. Один sheet без Next

```text
Купить / подключить домен
[Купить новый] [Есть доступ] [Через DNS]

Домены
[example.am]
[+ Добавить домен]

Поля выбранного сценария
[Сохранить / Начать покупку]
```

### Купить новый

Минимум для запуска из Product — доменное имя или список имён. Product известен из контекста. Прочие поля заполняются по мере готовности:

- провайдер и стоимость покупки, если известны; для разных провайдеров — соответствующие строки;
- клиентская цена после уточнения условий;
- существующий Credential либо отметка, что аккаунт ещё предстоит создать;
- один общий свободный текстовый блок «Данные клиента для регистрации» на покупку;
- ответственные, подставленные из Product; можно заполнить недостающие назначения.

Валюта по умолчанию AMD. Используется существующая поддержка валют. Не обозначать сумму в другой валюте как AMD и не вводить неявную конвертацию; если текущая модель не поддерживает нужную валюту, исполнитель должен явно описать необходимую совместимость до реализации.

Отдельных обязательных полей срока регистрации и ссылки оплаты в этой форме нет. Ссылка входа хранится в Credential. Существующие данные о сроке и периодичности сервиса сохраняют своё назначение; отсутствие UI-поля не означает удаления этих данных.

Данные регистрации можно добавить позднее. Они не копируются в обычное описание Task, глобальный поиск, уведомления или общедоступные notes. Один блок должен переиспользоваться для выбранных доменов; способ хранения выбирается при технической сверке. Существующие сведения используются повторно, но не считаются автоматически актуальными без проверки исполнителем.

### Есть доступ

Доменные имена и поле Credential: выбрать существующий либо «Создать Credential» внутри dropdown по общему паттерну NBOS. Созданная запись автоматически выбирается и связывается с сервисом. Незавершённую форму можно сохранить.

После реального подключения специалист отмечает «Подключение проверено». Это отделено от покупки. Новые Invoice и Expense только из-за подключения существующего домена не создаются. Кто оплачивает дальнейшее продление, задаётся существующим billing model отдельно от наличия доступа.

### Через DNS

Сохраняются доменное имя, явный способ «Клиент подключает сам / доступ не предоставлялся» и DNS-инструкции. Черновик можно сохранить и дополнить позже.

**Подтверждать фактическое подключение сайта в NBOS для этого сценария не нужно.** Не создаются ожидание проверки, обязательная Task проверки или domain stage gate по фактическому DNS-подключению. Даже если клиент подключится через месяц, этот сценарий не остаётся искусственно незавершённым.

Для завершения доменного требования достаточно зафиксировать способ и переданные DNS-инструкции. Это не отменяет независимые delivery-требования, не относящиеся к доменам.

Общая Credential-карточка «DNS» — legacy workaround. Новый признак заменяет её использование. Миграция проводится по явно подтверждённым ID и связям; не преобразовывать все записи с похожим названием. До сверки использования не удалять общую карточку, секреты или историю.

## 4. Ответственные и уточнение условий

- PM ведёт потребность и общение с клиентом; может передать сбор сведений Tech.
- Sales наследуется из Deal при создании Product. Для существующих Products отсутствие назначения заполняется явно, без угадывания исторического сотрудника.
- Tech назначается PM на этапе Starting.
- Sales и Tech должны быть определены к завершению Starting; при более раннем запуске потребности недостающие назначения заполняются в sheet. Не терять работу в неназначенной очереди.
- У конкретной работы по уточнению условий один ответственный. Sales может проверить обычную цену и выставить счёт; Tech может подобрать провайдера для необычной зоны. Если PM уже всё проверил, не создавать повторную проверку.
- Sales не является обязательным посредником каждой покупки. Используются назначенные исполнители и действующие права; принадлежность к Product сама по себе не разрешает финансовую операцию.

Данные клиента разрешено получать параллельно уточнению цены и оплате. В обычном процессе после оплаты автоматически поднимается только недостающая подготовка; уже выполненные действия пропускаются.

## 5. Tasks и место сохранения данных

Обычная Task не получает специальные поля аккаунта, стоимости или новую форму подготовки.

```text
Task: Подготовить покупку example.am
    → ссылка на Client Service
    → существующая карточка сервиса поверх задачи
        → выбрать / создать Credential
        → уточнить стоимость
```

Использовать существующее открытие связанных сущностей в sheet; пользователь возвращается к задаче без поиска в Finance. Если паттерн требует доработки, переиспользовать общий механизм, не создавать отдельный экран workflow.

При необходимости создаётся работа PM на получение данных и одна содержательная задача Tech на подготовку покупки: создание/переиспользование аккаунта, сохранение доступа, подготовка оплаты. Не создавать отдельные задачи ради каждого поля и Task Finance поверх Expense.

Одна Task может обслуживать несколько доменов одной покупки, если это одна реальная работа. В ней должны быть доступны все связанные сервисы. Повторная обработка событий не создаёт дубли задач.

Завершение Tech-задачи обновляет готовность Expense. Если данных не хватает, система предлагает добавить их или передать работу с пояснением и явным ответственным. Проблема остаётся видимой; фиктивный Credential для прохождения проверки не нужен.

## 6. Invoice, Expense и оплаты

### Отдельный счёт на каждый домен

Один submit с несколькими доменами создаёт отдельный Client Service и отдельный Invoice на каждый домен. Не добавлять invoice lines или many-to-many Invoice–ClientService ради объединения суммы.

Сообщение бухгалтеру остаётся в существующем формате отдельного Invoice с названием соответствующего сервиса. Свободный Invoice не запускает доменный процесс лишь по названию или текстовому упоминанию домена.

### Момент создания расхода

После подтверждения полной оплаты доменного Invoice NBOS создаёт или находит связанный Expense, **даже если аккаунт ещё не готов**. Частичная оплата учитывается существующей моделью Finance и не считается полной; ранняя выплата возможна вручную.

Сумма Expense:

1. отдельная подтверждённая стоимость провайдера, если указана;
2. иначе сумма Client Service, использованная для этого Invoice.

Fallback берётся из снимка условий конкретного счёта, а не из изменённой через год текущей цены сервиса. Finance может уточнить расход перед выплатой. Использование fallback не означает, что деньги уже потрачены; ExpensePayment отражает фактическую выплату. Не перезаписывать финансовую историю при редактировании сервиса.

### Связи

```text
Product
  ├── Client Service: example.am
  │     ├── Invoice этого приобретения/продления → Payment
  │     └── Expense того же приобретения/продления → ExpensePayment
  └── Client Service: example.com → свои Invoice / Expense
```

Product даёт контекст, Client Service — конкретный домен и аккаунт, Invoice/идентификатор операции отличает текущую покупку от следующего продления. Одного productId или «последнего расхода домена» недостаточно для безопасного сопоставления.

Для текущего объёма сохраняются существующие связи Expense с одним Client Service и Invoice. Групповые расходы для разных доменов не требуются.

### Credential появился позднее

Пустой Credential не блокирует создание Expense. Сохранённый позднее доступ на Client Service становится доступен из уже существующего открытого Expense автоматически.

Технический выбор — разрешённое получение текущей ссылки через сервис либо идемпотентная синхронизация пустой ссылки — фиксируется в плане до кодирования. Не заменять явно выбранный другой Credential молча и не переписывать оплаченные исторические расходы. Изменение связи не выдаёт право раскрыть секрет.

Finance видит расход и недостающую подготовку заранее, может обратиться к назначенной команде. Завершение задачи не должно быть единственным способом учесть готовую покупку: Finance вправе сам подготовить и оплатить, зафиксировав факты.

### Исполнение

Finance использует Expense, открывает связанный Credential по правам и фиксирует ExpensePayment. После подтверждения регистратора здесь же доступно «Домен зарегистрирован». NBOS запускает существующую проверку срока.

`Провайдеру оплачено`, `регистрация подтверждена` и `сайт подключён` — разные факты. Временная недоступность RDAP не требует повторной оплаты. Для DNS-сценария отдельного факта «сайт подключён» не требуется.

## 7. Продление и ручная оплата

Обычное продление использует действующий механизм проверки и Invoice примерно за 60 дней, с действующим dueDate и правилами уведомлений. После оплаты — связанный Expense. При рабочем аккаунте и отсутствии технической работы PM, Sales и Tech не участвуют, автоматической ежегодной Tech Task нет.

Если доступ неисправен, возникают конкретная задача и видимый блокер. Нормальные сервисы контролирует система, сотрудники разбирают исключения.

Уполномоченный Finance может вручную создать Expense из Client Service и оплатить до Invoice или до клиентской оплаты. Новый обязательный emergency approval workflow не вводится; сохраняются действующие финансовые права.

При позднем поступлении денег автоматика переиспользует расход того же продления, включая уже оплаченный. Если сопоставление не однозначно, запрашивается ручная привязка, а не создаётся второй расход. Фактические выплаты вне NBOS заносятся существующими средствами с первоначальной датой и подтверждением.

## 8. Delivery gate

Запуск из шапки доступен с начала Product, а не только на Transfer. Разработка не блокируется нерешённым доменным вопросом.

Перед завершением этапа переноса доменное требование проверяет:

| Вариант                    | Требуемый результат                                                                                                                           |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| Купили / клиент дал доступ | Конкретный домен связан с Product; реальный Credential сохранён; для покупки подтверждена регистрация; подключение проверено                  |
| Через DNS клиента          | Сохранены способ подключения без нашего доступа и переданные DNS-инструкции; Credential и подтверждение фактического подключения не требуются |

Выбор сценария сам по себе не означает выполнения работы. Кнопка из сообщения о недостающих данных открывает тот же sheet. Использовать существующий механизм stage requirements; не строить вторую систему gate.

При нескольких доменах требование относится к доменам, необходимым для переноса этого сайта; дополнительная покупка не должна неожиданно блокировать уже готовый основной сайт. Связь с фактическим доменным требованием определяется при подготовке этапа, не по всем сервисам клиента.

## 9. Архив и Cancel service

В существующем коде Cancel service сохраняет запись со статусом CANCELLED; hard delete запрещён; default list исключает CANCELLED, renewal selection исключает отменённые сервисы. Это уже основа архива, а не повод добавлять новую сущность.

Целевое поведение: история сохраняется, сервис можно найти в архивном представлении; новые автоматические обязательства и сервисные напоминания прекращаются. Существующие Invoice, Expense и долги не становятся оплаченными или отменёнными автоматически. Их обработка остаётся в Finance.

Перед изменением UI проверить list/board/filter, scheduler, notifications и дочерние Expense Plans. Не утверждать, что один статус уже останавливает все независимые генераторы. Переименование «Cancel service» в «Архивировать» допустимо после проверки соответствия поведения; новый архивный статус не требуется.

Не удалять Credential при архивировании одного домена: он может обслуживать другие домены. Для редкого отказа после оплаты специальный refund workflow не создаётся.

## 10. Доступ и безопасность

Использовать отдельное существующее право Client Services и актуальные права Expense Plans, Expenses, Invoices, Tasks и Vault. RBAC разделяется отдельной работой; не воспроизводить её и не копировать роль-списки.

Операционный доступ к Product/Task не выдаёт весь Finance. Перед открытием карточки проверяются сервисные права и контекст. Из удобного sheet нельзя обойти права создания Invoice, Expense или раскрытия Credential.

Developer не получает финансовую историю или регистрационные персональные данные только из-за участия в Product. PM видит разрешённые операционные сигналы. Tech получает необходимые данные регистрации в рамках поручения. Finance работает с выплатой; секрет раскрывается только отдельным разрешением Vault.

Свободный текст регистрации не является общедоступной заметкой. Проверить место хранения, field-level выдачу, аудит и отсутствие текста в логах, поиске, уведомлениях и стандартных Task payload. Не вводить новую универсальную PII-платформу, использовать существующие безопасные механизмы; если их недостаточно, выделить минимальную защищённую часть.

## 11. Устойчивость без жёсткой воронки

Хранятся реальные финансовые и операционные факты; UI вычисляет следующее действие и недостающие данные. Не создавать ручной глобальный enum, запрещающий нестандартный порядок событий.

Обязательны:

- повтор Start/submit/payment event не создаёт дубли сервисов, Invoice, Expense и Tasks;
- один домен уже найден — открыть/связать существующий, не создавать копию; проверка дублей не раскрывает чужие записи;
- для нескольких доменов частичный сбой показывает результат по каждому, повторяет только недостающие действия;
- Invoice не создан — потребность сохранена и видна, клиент не получает ложного сообщения о счёте;
- Task не создана — подготовка остаётся видимой с ответственным и безопасным повтором;
- worker восстановился — недостающие действия восстанавливаются штатной очередью/сверкой;
- ручная покупка и ручное продление сопоставляются с тем же циклом;
- NOT_FOUND/NO DATA используют существующие правила проверки, не означают подтверждение покупки;
- закрытый Product не запрещает новую покупку, сервис не архивируется вместе с delivery автоматически.

Точный способ идентификации цикла и восстановления событий — техническая часть реализации, а не новая пользовательская сущность. Проверять уникальность на уровне хранения, а не только отключённой кнопкой.
