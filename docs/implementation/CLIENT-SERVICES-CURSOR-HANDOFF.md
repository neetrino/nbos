# Client Services — промпт для реализации в Cursor

Скопировать следующий текст в задачу исполнителя. Он описывает реализацию утверждённого процесса, а не повторное проектирование.

```text
Реализуй согласованный доменный процесс NBOS по документам:
- docs/NBOS/02-Modules/04-Finance/08-Domain-Purchase-and-Connection.md
- docs/implementation/CLIENT-SERVICES-IMPLEMENTATION-PLAN.md

Сначала прочитай AGENTS.md, TECH_CARD, архитектуру, Documentation Hub и применимые модульные документы. Проверь git status и сохрани чужие изменения. Используй security-review, verify-before-completion и safe-database-migration при изменении схемы. Не выполняй production deployment/migrations, commit/push без запроса.

Начни с этапа 0: сопоставь целевое поведение с текущей реализацией. Затем выполняй этапы последовательно с проверками. Не считай описанный в каноне целевой функционал уже существующим. RBAC Client Services / Expense Plans разрабатывался отдельно — используй фактический результат, не строй вторую модель permissions.

Ключевые решения, которые нельзя переосмысливать:
1. Два входа: Product/Delivery и Invoice Board; оба ведут к одному процессу. Только Product selector, никаких Deal/Client tabs и покупки до Product.
2. В шапке открытой Delivery-карточки и страницы Product компактный элемент. Отдельного блока и кнопки на маленькой kanban-карточке нет. Один sheet без Next.
3. Три сценария: купить / есть доступ / через DNS клиента. В DNS-сценарии НЕ требуется подтверждение фактического подключения. Legacy Credential «DNS» заменяется явным способом после безопасной сверки.
4. Старт из Product допускает только доменные имена, цена уточняется позже. Валюта по умолчанию AMD. Не добавлять обязательные поля срока и ссылки оплаты; URL уже в Credential.
5. Общий свободный блок регистрационных данных защищён от неразрешённого чтения. Не внедрять RegistrantProfile ради этой задачи и не помещать PII в обычные Task notes.
6. Sales наследуется из Deal в Product; Tech назначает PM на Starting. Пропущенные назначения можно заполнить в sheet; конкретная работа имеет ответственного.
7. Каждый домен — отдельный Client Service и отдельный Invoice. Несколько доменов вводятся одним действием. Общий Invoice на несколько сервисов не делаем.
8. После полной оплаты клиента создаётся или находится Expense, даже если Credential ещё отсутствует. Сумма — отдельная стоимость покупки, иначе снимок суммы сервиса для этого Invoice. Finance вправе уточнить её.
9. Поздно добавленный Credential появляется в открытом Expense автоматически, с сохранением Vault permissions и без перезаписи истории. Один аккаунт переиспользуется несколькими доменами.
10. Task обычная, со ссылкой на сервис. Поля доступа и стоимости заполняются в Client Service, dropdown Credential содержит создание на месте. Отдельной Finance Task нет.
11. Ручное создание и оплата Expense до Invoice разрешены по действующим правам. Поздняя оплата клиента не создаёт дублирующий расход того же цикла.
12. Оплата провайдеру, регистрация и подключение — разные факты. RDAP уже существует. Обычное renewal без проблемы не требует PM/Tech.
13. Client Services остаётся в Finance, но операционные входы используют отдельные права. Не расширять доступ к финансовым данным или секретам из-за контекстной ссылки.
14. Cancel service — база архива; проверить реальное поведение всех генераторов. Сохранить историю и долги, не удалять данные. Специальный возвратный процесс не нужен.
15. Не строить workflow engine или новые Case/ProviderAccount сущности без доказанной необходимости. Устойчивое сопоставление циклов и идемпотентность обязательны.

Если существующая модель не поддерживает обязательный сценарий, предложи минимальное изменение и обоснуй по коду; не имитируй связь notes-полями и не обходи проверки. Не расширяй проект на редкие исключения.

Проверяй результаты каждого этапа: позитивные и негативные permissions, retries/duplicates, ручную оплату до клиентской, поздний Credential, многодоменный ввод и три сценария подключения. Запускай релевантные тесты, typecheck/lint, Prettier. Для UI проверь реальные экраны и mobile. Не маскируй ошибки и не заявляй непроверенное.

В конце обнови фактический статус реализации и дай короткий отчёт: что изменено, какие проверки прошли, что не проверено и какие операторские действия ещё нужны. Не выдавай документацию целевого поведения за готовый код.
```
