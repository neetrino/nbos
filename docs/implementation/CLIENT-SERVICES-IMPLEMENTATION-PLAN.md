# Client Services: план реализации согласованного доменного процесса

**Дата:** 2026-09-17. **Статус:** план, реализация этих этапов не заявлена завершённой.
**Источник:** [утверждённый канон](../NBOS/02-Modules/04-Finance/08-Domain-Purchase-and-Connection.md).

## 1. Исходное состояние и ограничения

На момент подготовки в основной ветке существуют ClientServiceRecord, Domain, Invoice с одной ссылкой clientServiceRecordId, Expense со связями Product/ClientService/Invoice/Credential, ручные flows, RDAP/WHOIS, Cancel service и отдельная работа по RBAC.

Это не доказательство завершения сквозного процесса. Проверить актуальный код перед реализацией. Не копировать незавершённые предположения из старого worktree. Не менять стек и modular monolith. Не выполнять production deploy/migrations, commit/push без запроса.

## 2. Этап 0 — техническая сверка

Прочитать AGENTS, TECH_CARD, архитектуру, канон и актуальные RBAC-документы. Проверить:

- Product ownership, Sales handoff из Deal, Tech assignment на Starting;
- фактические поля суммы/валюты и сериализацию Client Service;
- Invoice create и все пути подтверждения Payment, включая ручной Mark paid;
- текущую генерацию Expense/Tasks: не запускать второй обработчик поверх первого;
- task links и повторное открытие EntityDetailSheet;
- хранение DNS-способа, данных регистрации и подтверждения покупки;
- permissions Client Services/Expense Plans и актуальные scopes после независимой RBAC-работы;
- Cancel service, выборку renewal, reminders, linked Expense Plans;
- действующие проверки и уникальные ограничения циклов.

Выдать краткую карту «есть / доработать / минимальная миграция» до изменения схемы. Определить устойчивый ключ покупки/renewal, корреляцию с вручную созданным Expense, атомарность и восстановление. Не считать дату, последнее событие или productId уникальным циклом.

Если нужны поля, защитить существующие данные и выполнить safe-database-migration. Не добавлять ServiceOperation, ProviderAccount или RegistrantProfile по одному лишь наличию этих названий в прежнем обсуждении.

Приёмка: технические решения соответствуют канону, не требуют лишних пользовательских шагов и не расширяют объём.

## 3. Этап 1 — данные, связи и существующие домены

Реализовать явный DNS-сценарий и разрешённые операционные данные. Credential selector содержит создание на месте. Переиспользование аккаунта не создаёт копию секрета и не меняет grants. Защитить свободный блок регистрационных данных.

Подготовить безопасный перенос legacy «DNS» по проверенным ID; dry-run и отчёт по связям, без удаления карточки. Не преобразовывать пустой Credential в «доступ никогда не предоставлялся» автоматически.

Приёмка:

- два домена / два Products могут ссылаться на один аккаунт;
- создание Credential в Client Service сразу выбирает и сохраняет ссылку;
- DNS сохраняется без Credential и без подтверждения подключения;
- existing-domain save не создаёт Invoice/Expense;
- пользователь без нужных прав не видит секреты/PII/чужие финансовые записи.

## 4. Этап 2 — единый вход Product / Delivery

Добавить компактный элемент в шапки, единый sheet без Next, условные поля трёх сценариев, список доменов и добавление следующего. Не добавлять блок Overview и кнопку на маленькую kanban-карточку.

Подставить ответственных из Product. Sales переносится из Deal при создании Product; Tech задаётся PM на Starting. Предусмотреть заполнение пропусков на действующих Products без массового угадывания.

Приёмка:

- запуск только с именами сохраняет потребность;
- неизвестная цена не препятствует старту;
- новая покупка после закрытия delivery запускается с Product;
- несколько доменов и повторный submit не дублируют сервисы;
- состояния «Куплен», «Подключён», «Через DNS клиента» не смешиваются;
- мобильный вариант помещается в шапку; не перекрывает закрытие sheet и меню.

## 5. Этап 3 — второй вход и Invoice

В Invoice Board добавить путь «Покупка домена» рядом с текущим свободным созданием. Один dropdown Products, без Deal/Client tabs. Для известной цены создаётся сервис и счёт; существующая открытая потребность переиспользуется.

Несколько доменов → отдельные Invoice, каждый со своим Client Service. Сохранить official invoice subprocess, бухгалтерские сообщения, tax/company/contact и разрешения.

Приёмка:

- Product-путь и Invoice-путь приводят к тем же сущностям;
- на каждый домен отдельная сумма и Invoice;
- свободный Invoice с текстом домена не запускает автоматику;
- ошибка создания одного Invoice видна и допускает безопасный повтор;
- нет изменений many-to-many / invoice line items ради группового счёта.

## 6. Этап 4 — оплаченный Invoice, подготовка, Expense

Подтверждённая полная оплата запускает создание/поиск Expense и недостающую человеческую подготовку. Известные аккаунт/данные/подготовка переиспользуются. Обычные Tasks связываются с Client Service, новых доменных полей в Task нет.

Сумма расхода: отдельная стоимость, иначе снимок суммы сервиса для соответствующего Invoice. Finance может изменить её перед оплатой. Отсутствие Credential не препятствует созданию расхода.

Выбрать и проверить способ появления позднего Credential в открытом Expense. Не заменять вручную выбранный иной доступ и исторические оплаченные записи. Не делать task completion единственным источником финансового факта.

Приёмка:

- Payment до подготовки создаёт Expense без аккаунта;
- сохранение аккаунта позднее делает его доступным из Expense по правам;
- два повторных Payment events не создают два расхода или две задачи;
- частичная оплата не считается полной;
- Finance может оплатить вручную раньше, поздняя оплата клиента не дублирует расход;
- неопределённое сопоставление требует ручной связи, не повторной выплаты;
- повтор запуска после сбоя worker достраивает только недостающее;
- Finance работает без отдельной Task и кнопки передачи от Tech.

## 7. Этап 5 — завершение, gates, renewal и архив

Finance фиксирует ExpensePayment и отдельно подтверждение регистрации. Использовать действующую RDAP-проверку. Gate на завершении переноса различает реальный доступ и DNS клиента. Дополнительная покупка не блокирует основной сайт автоматически.

Обычное продление сохраняет существующее окно Invoice и reminders, создаёт Expense после оплаты и не требует Tech/PM без технической причины. Сервисный генератор и Expense Plan не создают два обязательства одного цикла.

Сверить Cancel service с архивным смыслом: сохранение истории, поиск архива, исключение из активного реестра, прекращение новых автоматических действий. Существующие долги не списываются. Название «Архивировать» не заменяет проверки поведения. Специальный refund flow не реализуется.

Приёмка:

- оплачено ≠ зарегистрировано ≠ подключено;
- NO DATA не повторяет оплату и не уничтожает последний известный срок;
- DNS не требует подтверждения фактического подключения;
- у сценария с доступом gate требует сохранённый реальный Credential;
- renewal с рабочим доступом не создаёт обязательную ежегодную Tech Task;
- архивный домен не порождает новые автоматические счета, история и общий Credential сохранены;
- ручной расход текущего renewal переиспользуется, прошлогодний — нет.

## 8. Проверки и передача

На каждом этапе — релевантные unit/integration tests, permissions checks, typecheck/lint по затронутым пакетам, Prettier на затронутых файлах. Для UI выполнить browser-проверку полного пути на desktop/mobile и негативных прав; для schema — безопасная миграция на тестовой БД. Не заявлять успешность непроведённых проверок.

Ключевая end-to-end цепочка: Product → несколько доменов → уточнение → отдельные Invoice → Payment → подготовка → Credential → Expense → ExpensePayment → подтверждение регистрации → gate. Повторить старт через Invoice Board и оба existing-domain сценария. Проверить восстановление после частичного сбоя и manual-first payment.

Полноценную security-review провести перед завершением: поля регистрации, Vault, nested finance responses, scoped ownership, cross-module actions, фоновые пользователи. Новое удобное действие не должно обходить текущую RBAC.

Порядок внедрения: additive изменения и defaults → совместимые API → UI → управляемое включение автоматизации после сверки существующих открытых записей. Не запускать массовую генерацию по историческим Invoice без dry-run. План отката отключает новую автоматику, сохраняя созданные финансовые факты.

Обновлять статусы реализации только после фактической проверки. Финальная передача: список изменённых файлов, реальные результаты checks, необходимые локальные миграции/операторские действия, оставшиеся ограничения. Production действия выполняет владелец отдельно.
