# Начальное наполнение каталога и конфигурация владельца

Цель: подготовить полезную библиотеку крупных работ без вымышленных финансовых договорённостей. [Канон](../../NBOS/03-Business-Logic/11-Delivery-Compensation-Configurator.md).

## 1. Seed-политика

- Отдельный идемпотентный seed/script для delivery catalogue, не повторный полный `prisma/seed.ts` со сбросом данных.
- Stable `code` для lookup; создавать отсутствующее, сохранять изменённое владельцем. Повторный запуск не переписывает контент, units, статус, attachments или memberships.
- Default dry-run показывает только операции и ids, без secrets; explicit apply только к подтверждённой среде.
- Production-safe seed создаёт draft definitions/content skeleton, без опубликованных units/rates, без employee assignments и BonusEntry.
- Поля units не заполнены → не ноль. Финансовый status `DRAFT/NOT_CONFIGURED`; опубликованный бесплатный норматив — отдельное явное решение Owner.
- Для тестов отдельный fixture с синтетическими published значениями. Не включать fixtures по условию вроде «таблица пуста» в production boot.
- После seed команда не обязана оценить каждую функцию. Owner публикует нужные в работе, остальные могут оставаться draft.

## 2. Кандидаты начальных крупных функций

Это стартовые описания, которые команда уточняет. Они не обязаны быть дополнением для всех продуктов: Owner задаёт «Входит в базу для…». Иконки выбираются из уже установленного lucide набора/allowlist.

| Stable code | Название | Граница работы / что проверить при приёмке |
| --- | --- | --- |
| BANK_PAYMENT | Банковская оплата | Один согласованный gateway: checkout, подтверждение платежа, обработка повторных событий и ошибок, тестовый успешный/неуспешный сценарий |
| WAREHOUSE_INTEGRATION | Интеграция со складом | Одна внешняя система, согласованные товары/остатки/заказы, направление обмена, retry и сверка |
| ERP_INTEGRATION | Интеграция с ERP | Согласованные сущности и mapping одной ERP; права, ошибки, повторный обмен без дублей |
| CRM_INTEGRATION | Интеграция с внешней CRM | Согласованная передача лидов/заказов/контактов; source mapping, авторизация, ошибки |
| CATALOG_IMPORT | Массовый импорт каталога | Источник, mapping, медиа, дубли, обновление, пробный импорт и сверка |
| DATA_MIGRATION | Миграция данных | Согласованный legacy dataset, очистка/mapping, dry-run, сохранность связей, план переключения |
| DELIVERY_PROVIDER | Интеграция службы доставки | Один provider, расчёт/создание отправления, tracking/status mapping, ошибки |
| CUSTOM_CHECKOUT | Нестандартный checkout | Отличия от базового checkout, валидация, совместимость оплаты/доставки, mobile flow |
| MULTILINGUAL_CONTENT | Дополнительная языковая версия | Согласованные языки, маршруты/переключение, контент и fallback; не включать стоимость перевода автоматически |
| ADVANCED_SEARCH | Расширенный поиск | Согласованный каталог/фильтры/ранжирование, обновление индекса, контрольные сценарии |
| CUSTOMER_PORTAL | Личный кабинет клиента | Согласованные экраны, авторизация, доступ к своим данным, история операций |
| ADVANCED_ROLES | Сложные роли и права | Матрица действий и данных, серверные ограничения, тесты запретов |
| MARKETPLACE_VENDORS | Мультивендор | Согласованная изоляция продавцов/каталогов/заказов; финансовые выплаты продавцам только если явно входят в объём |
| BOOKING_FLOW | Запись и бронирование | Ресурсы, доступность, отмена/перенос, защита от двойного бронирования |
| RECURRING_CHECKOUT | Подписочная оплата в продукте клиента | Разовая реализация customer billing-flow; НЕ ежемесячный бонус команде NBOS |
| CUSTOM_REPORTS | Нестандартные отчёты | Согласованный набор метрик/источников/выгрузок и контроль расчётов |
| EXTERNAL_AUTH | Внешняя авторизация / SSO | Один согласованный provider, привязка аккаунта, login/logout/error и security review |
| NOTIFICATION_INTEGRATION | Внешний канал уведомлений | Один provider/channel, согласованные события, retry/dedup и privacy |
| ONE_TIME_SEO_SETUP | Разовая техническая SEO-настройка | Согласованный аудит/исправления, sitemap/indexing/meta и отчёт; без ежемесячного продвижения |
| ADVANCED_ANALYTICS | Расширенная аналитика продукта | Согласованная event map/provider, consent при необходимости, тест событий и отчёт |
| CUSTOM_DEPLOYMENT | Нестандартное развёртывание | Дополнительные окружения/инфраструктура относительно базы, reproducible steps, проверка доступности и handover |

`BANK_PAYMENT` описывает работу над продаваемым клиенту продуктом; это не разрешение реализовать банковскую интеграцию/сверку в собственном Finance NBOS. Этот пакет создаёт каталог/расчёт, а не выполняет перечисленные интеграции за клиентов.

Стандартные navbar, footer, карточка товара, мелкие исправления, обычные review/QA задачи не превращать в обязательные отдельные платные пункты. Три design modes задаются базовым профилем, не дублируются тремя extras.

## 3. Шаблон инструкции функции

Каждая draft карточка получает структурированный шаблон, без вымышленных vendor-specific инструкций:

1. Назначение и ожидаемый результат.
2. Что входит / что не входит.
3. Необходимые исходные данные (ссылки на документацию; не raw secrets).
4. Шаги исполнения, заполняемые специалистом по реальной практике.
5. Проверки готовности, негативные сценарии.
6. Частые ошибки и особенности готовой базы/white label.
7. Материалы: ссылки, изображения, Files.

Не выдавать непроверенный шаблон за полностью готовый SOP. При публикации content editor подтверждает наличие полезного описания и критериев приёмки. Owner отдельно публикует финансовую норму.

## 4. Начальные базовые профили

В первую очередь подготовить draft профили для фактически используемых направлений: Website (существующие COMPANY_WEBSITE/LANDING/BUSINESS_CARD_WEBSITE), ECOMMERCE, CRM, MOBILE_APP, WEB_APP и разовая SEO. Не переименовывать existing ProductType enum в обобщённый Website.

Размеры конфигуратора: SMALL, CLASSIC, LARGE, VERY_LARGE, ENTERPRISE. Основы: FROM_SCRATCH, EXISTING_BASE, WHITE_LABEL. Дизайн: AI_DESIGN, CONCEPT, FULL_DESIGN, дополнительный вариант AI reviewer.

Не seed-ить сотни бесполезных комбинаций. Owner создаёт нужные профили через UI, указывает стандартный объём, роли/units и включённые функции. Для непубличного admin preview можно иметь один synthetic demo profile только в тестовой среде.

Extension использует собственный draft base profile: не наследует автоматически денежный base parent Product. Вводимые PM параметры подбирают конкретный extension profile; если он отсутствует, readiness объясняет настройку Owner.

## 5. Что публикует Owner перед первым реальным запуском

1. AMD/unit по каждой используемой роли; не брать цифры из зарплаты сотрудника автоматически.
2. Нужные base profiles, включая полную matrix required/unused/zero ролей.
3. Дополнительные функции, которые действительно нужно оплачивать отдельно.
4. Membership included-in-base; убедиться, что базовые units действительно покрывают работу этих функций.
5. Дату действия версии и результат preview на знакомом реальном scope.

Сравнение с историческим продуктом проверяет разумность scope/трудоёмкости, но не копирует его старую денежную выплату. Изменение тарифа и норматива не пересчитывает старые обещания.

## 6. Network seed

Отдельные stable policy identifiers на три payment models. Classic 4/1, first subscription 40/10, recurring 0/0. Не создавать дубликаты при rerun и не возвращать отредактированные Owner ставки к default. При несовпадении сегодняшнего Client с baseline — сообщение в dry-run/report, без мутации Client или автоматического rate-copy.

Исторический `SALES + NETWORKING` и новый `NETWORK` существуют независимо. Для перемещения старых сделок потребуется отдельное явное решение; этот seed не меняет источники сделок.
