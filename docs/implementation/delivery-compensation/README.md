# Delivery Compensation v2 — пакет для последовательной реализации

**Дата:** 2026-09-18. **Статус пакета:** документация подготовлена; реализация всех фаз НЕ начата.

## Что именно построить

- Общий Каталог функций с инструкциями/материалами и закрытыми units.
- Базовые профили Product/Extension и тариф unit отдельно для каждой из шести ролей.
- Конфигуратор продукта: база + крупные допфункции, правила included-in-base.
- Версионный расчёт и idempotent материализация плановых бонусов при первом Development.
- Изменение scope, ручное распределение при замене исполнителя, безопасная отмена невыполненного.
- Wallet-only личные денежные данные; Product/Delivery — рабочая информация без бонусов.
- Полная совместимость с существующими bonus pool, release, payroll, expense payments.
- Network в CRM и стартовые policy rows, без переделки Seller engine.
- Безопасные seed, admin readiness, тесты и инструкции запуска.

## Что специально не включать

Обязательный R&D workflow, премия за автоматизацию, ежемесячный delivery, публичные units, персональные employee rates, генератор клиентской цены/себестоимости, новая задача за каждую функцию, интеграция Credential с каталогом, production операции. Эти идеи обсуждались, но не вошли в текущую реализацию.

## Последние решения, которые нельзя потерять

- База имеет свои units: это НЕ сумма всех included-функций. Included-функции повторно не оплачиваются.
- Не создавать обязательный placeholder неизвестной работы. PM не должен каждый раз просить CEO определить units.
- Создать/оценить функцию после выполнения конкретной работы и добавить к активному продукту — допустимо.
- Только Owner/CEO задают units/rates/финансовые правила. Редактор инструкции не получает такое право.
- Команда не видит units ни в каталоге, ни в Product, ни в Wallet. В Wallet видит собственные деньги.
- Все поля распределения при замене — пустые и обязательные; никаких default процентов.
- Не начислять в Starting. Первый Development создаёт прогноз, не выплату.
- Нормативы и тарифы меняются версиями; скорость сотрудника не уменьшает обещанный бонус.
- Старые продукты можно пропустить. Наличие в БД legacy-записей не означает разрешение удалить/пересчитать их.

## Что ещё предстоит заполнить владельцу

Реальные суммы тарифов и units по базовым профилям/функциям не согласованы численно. Это нормальная настройка готового приложения через admin UI, а не причина остановить разработку. Production seed содержит только draft контент; тестовые деньги живут только в fixtures/demo. Неполная конфигурация блокирует первый Development новых model-managed продуктов, но не все legacy процессы.
